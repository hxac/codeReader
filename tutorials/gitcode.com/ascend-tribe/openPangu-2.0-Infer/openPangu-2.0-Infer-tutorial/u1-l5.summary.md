本讲以已部署的 1P1D BF16 服务为靶场，覆盖三个最小模块。请求测试：客户端只认 C 节点 proxy 的 7000 端口（proxy_port 决定），proxy 以 sequential 策略编排「先 prefill 后 decode」，请求体 model 必须与 SERVED_MODEL_NAME 完全一致否则报 4xx；流式请求走 SSE 增量块并以 data:[DONE] 收尾，非流式一次性返回完整 JSON。日志跟踪：日志分四层——脚本层 run_prefill/run_decode.log（拉起失败首看）、引擎层 server_N.log（P 机 1 个、D 机 16 个）、代理层 nginx_*.log、fetch_log 汇总层；服务就绪判据是 server_0.log 出现 Application startup complete。故障排查：按决策树自上而下（连通性→4xx→就绪标志→HCCL 通信→跨机网卡），核心是 HCCL 多机建链失败的修复——在模板命令中显式 export HCCL_SOCKET_IFNAME 指定正确网卡（GLOO/TP 网卡则由 ansible 自动探测），建链超时默认 1800 秒，网卡配错常表现为长时间卡住后超时。
