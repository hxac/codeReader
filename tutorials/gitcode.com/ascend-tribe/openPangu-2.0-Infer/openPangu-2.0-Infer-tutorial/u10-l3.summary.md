本讲是专家层实战，把四类二次开发扩展点收拢成一张地图并各配动手操作。补丁扩展：新补丁继承 VLLMPatch、用 register_patch 注册进 PatchManager，文件放 patches/common（必然注册）或 patches/models/<模型>（按 model_type 匹配），OMNI_NPU_VLLM_PATCHES 决定应用名单，须先在模块级保存原实现再包装回调，两级去重防撞符号，以「successfully applied patches」日志验证。配置扩展：新模型按四步登记——match_hf_configs.json 指纹（字段逐值相等才命中）、定 high_throughput/low_latency 场景、best_practice_configs.json 按模型×硬件×精度路由、落盘两段式 json；CUSTOM_MODEL_CONFIG_PATH 是最高优先级覆盖通道但只接受 configs 下相对路径，拼错键被静默丢弃，以 ModelExtraConfig 回显验证。connector 扩展：kv_connector 名字经 KVConnectorFactory 注册表（名字→字符串路径、延迟 import）解析，内置 LLMDataDistConnector 防御式注册，第三方经 omni.kv_connectors entry point 注入，自研参考「门面+四协作类」架构。装饰器扩展：plugin_decorators.py 在模型加载、输入准备、注意力、前向、输出等挂点提供 pre/post 钩子，pre 返回 dict 改入参、conditional 版返回 True 可整体替换原函数，经 omni.*_decorators entry point 组挂钩。开发工作流：容器内 omni-npu 为可编辑安装，docker exec 直接改源码后重跑 run_server 生效。方法论是按「要改谁的行为」选扩展点，一切以启动日志为证据。
