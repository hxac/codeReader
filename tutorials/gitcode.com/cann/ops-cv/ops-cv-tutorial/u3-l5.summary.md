本讲走读算子 op_host 侧的 def 文件（`*_def.cpp`）及编译注册链路。核心内容：def 文件用继承 `OpDef` 的类以链式调用声明输入输出端口的 dtype/format、属性（Attr）、`OpAICoreConfig` 编译配置与芯片绑定（`AddConfig`），最终由 `OP_ADD` 宏借助全局对象构造完成注册；def 只声明「是什么」，不含计算逻辑。关键概念包括：op_type（类名）与目录名两套命名、dtype 语义分「任选列表」与「按列对齐的映射表」（一列即一种合法组合、对应一个预编译二进制）、`ValueDepend`（支撑 Infershape 常量推导）、`opFile.value`（绑定 kernel 实现文件）、`AddConfig`（决定芯片支持范围）。编译链路为：def 编成动态库 → opbuild 工具加载注册表，自动生成 aclnn 接口代码与算子信息 ini → gen_ops_info.cmake（以 grep 解析 def）生成 ops-info.json 并驱动 opc 编出 kernel 二进制；`config/<芯片>/` 下 binary.json（手工二进制清单，缺省自动生成）与 simplified_key.ini 为可选芯片级覆盖层。结论：def 是「一份声明、多处消费」的单一事实源，与 README、config 目录构成三方契约，修改算子能力须三方同步。下一讲转向 common 公共基础设施。
