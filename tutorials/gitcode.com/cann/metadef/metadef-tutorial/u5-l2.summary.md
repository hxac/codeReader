本讲剖析 metadef 通用插件装载底座 `PluginManager`（inc/common/plugin/plugin_manager.h 与 base/common/plugin/plugin_manager.cc），其工作分三阶段：路径搜索（GetOpsProtoPath 等静态函数按「自定义环境变量 > vendors/config.ini 各厂商 > built-in」优先级拼出冒号分隔路径串）→ dlopen 加载（LoadSo 路径串通道与 Load 目录通道，默认 RTLD_NOW|RTLD_GLOBAL，受 64 个/单库 800MB/累计 1000MB 三重限额防护）→ 符号解析（func_check_list 逐个 mmDlsym 做「类型身份证」校验，缺符号即 dlclose 丢弃）。核心结论：错误处理哲学是「单 so 失败跳过、流程继续」，函数级返回几乎恒 SUCCESS，仅符号缺失升为 ERROR 并上报 E19999；IsVendorVersionValid 用 required_opp_abi_version 区间拦截 ABI 不兼容的厂商包；句柄由 handles_ 以 RAII 管理，重复 Load 先清空旧句柄；上层经弱符号 SetMetadefPluginCustomOpLibPathForC 注入路径以解除依赖环。它与 u4-l5 的 OppSoManager 互补，共享 mmpa 的 mmDlopen/mmDlsym 封装与「dlopen 瞬间静态对象完成注册」机制，正式取数仍由上层两步 dlsym 协议完成。单测展示了 system 造目录、mmpa stub、稀疏文件等文件系统测试技巧。
