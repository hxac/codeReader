本讲义剖析 `src/hixl/engine/` 下的 ClientHandler 体系：`IClientHandler` 是 HixlClient 与 CS 层之间的策略抽象，接口面与 Hixl 传输类公开 API 一一对应（建链、内存注册、同步/异步传输、状态查询、资源释放、Dump），唯通知走控制面 socket 不经过它。两个实现：`DirectClientHandler` 只消费 matched_pairs[0]、一对一封装 CS 层 C 接口（Put/Get 对应 WRITE/READ），适用于 HCCS/RoCE/UBOE/UB_RTP 单协议链路，一个 TransferReq 对应一个 CompleteHandle，首查终态即摘表；`UbClientHandler` 面向同实例 UB 场景，按 `map<CommType, handle>` 持有多条链路，核心是 `ClassifyTransfers`——用本端/对端注册内存区间表（local_segments_/remote_segments_，后者经控制面一次性拉取）推导每个 op 的内存类型组合并分桶选路，一个 TransferReq 聚合多个 BatchHandle，状态查询呈「全完成才算完成」的聚合语义。关键术语：`CommType`（UB_D2D/H2D/D2H/H2H 四种内存路径 + 四种协议类型）、懒惰建链（`is_lazy` 源自引擎 auto_connect 选项，首次 Connect 只记账，建链推迟到首次传输且只建所需类型）。handler 类型由 `EndpointMatcher` 静态优先级规则表决定：同实例优先 UB 分组（另有「全 device ub_ctp 仅 D2D」特例），其余含全部跨实例场景走 DIRECT；全部落空返回 PARAM_INVALID。`ClientHandlerFactory::Create` 仅做二选一分派，`HandlerCreateArgs` 是贯穿参数包，`ClientHandlerConfigHelper` 负责把 qos/max_active_channels 可选项译成 JSON 串（空配置返回空串）。完整分派路径：Hixl::TransferAsync → HixlImpl 门卫 → HixlEngine（auto_connect 探活）→ HixlClient（状态校验 + req_map_ 登记）→ handler → CS C 接口。
