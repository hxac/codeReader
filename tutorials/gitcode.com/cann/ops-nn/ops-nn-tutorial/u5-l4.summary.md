本讲是 u5 单元收官，围绕「高性能与快速下发」两大主题。核心结论：端到端耗时＝Host 侧启动开销＋kernel 执行时间，小而高频的算子（如 elementwise add）受 launch 路径影响最大，这正是 fast_kernel_launch 的优化对象。示例 `add.cpp` 单文件四合一：用 `TORCH_LIBRARY_FRAGMENT` 注册 Schema、`add_meta` 承接 InferShape/InferDtype、Ascend C kernel 就地实现、`PrivateUse1` 注册 NPU 实现——各层职责不变、载体合并。tiling 从独立回调加 TilingData 字节契约退化为就地函数调用，切分标量经 `<<<>>>`（grid/workspace/stream）核函数启动语法直接传入 kernel，类型分派由 Host 侧 `AT_DISPATCH_CASE` 完成；但启动仍须包在 `RunOpApi` 容器内以保持与 TorchNPU 的 aclnn 时序一致。该方式牺牲通用性（无 aclnn 接口、不支持图模式），仅适合场景封闭的自定义算子。Device 侧则由 ops-tensor 分层结构（ProblemShape/BlockScheduler/BlockMmad/BlockEpilogue 组合成 GemmUniversal）优化 Cube 类 matmul 算子，消除手工偏移量计算，构建期按固定 commit 拉取。fast_kernel_launch 优化 Host 侧、ops-tensor 优化 Device 侧，二者正交可组合。
