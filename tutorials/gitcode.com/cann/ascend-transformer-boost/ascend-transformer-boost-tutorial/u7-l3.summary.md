本讲围绕「如何系统化、数据驱动地测试一个 ATB 算子」展开，核心是「数据与引擎分离」的设计：用例写在 CSV 里，引擎写在测试框架里，新增用例通常只改数据。

测试目录按「测哪一层」分层：`framework/` 是测试引擎（编译出 `libatb_test_framework.so`），`apitest/opstest/` 是算子级 CSV 测试，`unittest/` 是框架内部 GTest（不依赖 NPU），`infratest/cinterface/kernelstest/fuzztest` 分别测基础设施、C 接口、Kernel 与鲁棒性。`build.sh` 把各 CMake 开关封装成子命令。

`operation_funcs.cpp` 是 JSON 与 Param 的翻译官：每个算子一个 `XxxOperationCreate` 函数，用 `contains` 守卫逐字段回填、枚举显式转型、`rsv` 单独拷贝，最后调模板版 `CreateOperation`；所有函数登记进 `g_funcMap`（算子名→工厂函数注册表），由字符串版 `CreateOperation(opName,param,&op)` 运行时分派。CSV 驱动测试按 Create/InferShape/Setup/Execute 四段式执行，每段比对 `ExpectedError`（带阶段前缀 `C:/I:/S:`）并计时；精度靠 `golden`（CPU 参考实现）按 `OpTypes` 分档比对。Python `OperationTest` 是另一条轻量路径，子类只需实现 `golden_calc` 与 `test_xxx`，与 CSV 共用同一 `OperationTorch` 桥接。注册名一致（CSV 的 `OpName`、`g_funcMap` 键名、`data_generation.py` 类名三者完全一致）是分派正确的前提；反例靠 `ExpectedError` 标注期望失败阶段，常用非 0 `rsv` 构造反例验证版本闸门。
