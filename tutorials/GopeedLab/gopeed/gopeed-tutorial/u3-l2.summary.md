本讲回答「一个 URL 交给 Downloader 后如何选中协议」，覆盖四个最小模块：FetcherManager 接口、SchemeFilter.Match 匹配语义、DownloaderConfig.Init 的默认注册顺序、parseFm/buildFetcher 的路由调用点。核心结论：FetcherManager 是协议级单例门面，集身份（Name）、路由声明（Filters）、工厂（Build/ParseName/AutoRename）与持久化契约（Store/Restore 两段式）于一身，Fetcher 才是任务级有状态执行者。SchemeFilter 用三种「URL 指纹」匹配：url（scheme 前缀加冒号边界）、file（先剥 query/fragment 再比扩展名）、base64（data URI 的 MIME），均大小写不敏感。路由是 first-match-wins：parseFm 按注册顺序双重循环取首个命中的管理器，全不命中报 ErrUnSupportedProtocol，因此注册顺序即优先级。默认顺序 ftp→hls→http→bt→ed2k，原则是「scheme 强意图优先于扩展名弱信号」：ftp://host/x.torrent 走 FTP，https 的 .torrent 由 HTTP 先下载种子文件本身，再经 AutoTorrent 链式建 BT 任务。路由贯穿任务全生命周期六个时刻（解析、直建、落库、选项、恢复、重试），恒以当时 URL 为准，并辐射决定协议配置分桶与 task.Protocol 标签。
