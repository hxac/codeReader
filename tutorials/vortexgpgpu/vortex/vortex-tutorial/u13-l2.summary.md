本讲讲 Vortex 这类「SimX + RTL 双引擎」项目的调试方法论，核心模块有四：`--debug=<level>` 旋钮、`ci/trace_csv.py` 清洗器、SimX-as-oracle 方法论、源码级内核调试与 Perfetto 可视化。关键术语先立：trace（`run.log` 运行时按周期打印的状态日志）、UUID（调度器在 schedule 阶段为每条指令分配的全局唯一编号，是连接 SimX 与 RTL、连接 trace 行与 CSV 行的「主键」）、oracle（被无条件信任为正确的一方，Vortex 选 SimX）、DTM/Debug Module（符合 RISC-V External Debug 规范的片上调试模块）。

核心结论是：`--debug` 经编译期宏 `VX_DBG_DEBUG_LEVEL` 门控 `DP/DT` 打印宏，diff trace 用 `--debug=3`，改源码须加 `--rebuild=1`；trace_csv 把无结构日志按 UUID 归并、清洗成 8 列 CSV 并按 UUID 排序，使两侧可直接 `diff`，首处分歧即 bug 锚点。SimX-as-oracle 是最关键方法论：当 RTL 调试陷入僵局（bug 跨模块、忍不住到处撒 `$display`），不要戳 RTL——（前提：让 SimX 镜像 RTL 结构）先让 SimX 过测试，再两侧加匹配 CSV dump 后 diff，故不能反过来用 RTL 当 oracle，因 rtlsim 开箱只给输出值与断言失败，SimX 才可断点插桩。设备内核逻辑错误另走 GDB+OpenOCD+simx `-d` 三端链路（三者 XLEN 须一致），性能形态问题用 `ci/perfetto.py` 转 Perfetto JSON 可视化。本讲与 u7-l4 model_parity 一体两面：一个是「平时保持一致」的纪律，一个是「一旦不一致」的排障流程，共享「绝不放宽容差吸收差异」的底线，并为 u13-l3 性能计数器分析奠基。
