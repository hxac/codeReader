# 行存储器 sharp_linemem 的循环缓冲

## 1. 本讲目标

本讲打开上一讲（u3-l3）里被当作「黑盒」使用的 `sharp_linemem`，搞清楚它如何用一块 RAM 把数据「延迟一行」。读完本讲你应该能够：

- 说清为什么行存储器需要 **1280 项** RAM，以及它和 **720p** 分辨率的对应关系；
- 读懂 `wr_address` / `rd_address` 两个地址指针的循环递增与回绕逻辑；
- 理解 `write_en = de_in` 这条写使能与「读改写」时序如何配合，最终实现「上一行同列像素」的取出。

本讲只聚焦 `sharp_linemem` 这一个模块；它如何被 6 级级联拼成 7 个垂直抽头，已在 u3-l3 讲过，这里不再重复。

---

## 2. 前置知识

在进入源码前，先用一句话建立直觉：

> 视频是一行一行、一个像素一个像素地流过来的。要做「垂直方向」的滤波（把上下相邻行的像素加权求和），就必须能拿到「上一行同一列」的像素。可是当前正在流入的是「本行」的像素——「上一行」的像素早在 1280 拍之前就流过去了。所以要把它**存起来**，等到 1280 拍后再读出来。

这里有两个关键词，初学者务必先分清：

- **720p 的分辨率是 1280×720**：横向每行 **1280** 个有效像素，纵向共 **720** 行。注意「720p」里的 720 指的是**纵向行数**，而**一行有 1280 个像素**。本讲的 RAM 深度 1280，正对应「一行的有效像素数」。
- **de（Data Enable，数据有效）**：只在有效像素区为 1，在行/场消隐期（blanking）为 0。它既是视频时序信号，在本设计里又被直接当作行存储器的**写使能**（见 u3-l2、u3-l3）。

如果你对 `sharp_slice` 如何例化 6 个 `sharp_linemem` 还没印象，建议先回看 u3-l3 的「垂直抽头链」一节。

## 4. 核心概念与源码讲解

### 4.1 行存储 RAM 阵列

#### 4.1.1 概念说明

要做垂直滤波，就需要「上一行、上上一行……同列」的像素。最朴素的想法是：把整整一行像素都存下来，等下一行流到同一列时，刚好能把上一行同列的像素取出来。

这就是「行存储器（line memory）」的职责——它不是存整帧图像，而是**只存一行**，并且每个时钟一边写入新像素、一边读出「一行前」的旧像素。

那么这一行有多少个像素？对 720p：

\[ \text{每行有效像素} = 1280,\qquad \text{行数} = 720 \]

所以一块 1280 项的 RAM，恰好装下「一行的有效像素」。

#### 4.1.2 核心流程

行存储器的核心是一个「延迟线」，其延迟长度等于一行有效像素数：

\[ \text{延迟长度} = 1280 = \text{一行有效像素数} \]

宏观流程：

1. 像素按 `clk` 节拍流入 `data_in`。
2. 每来一个有效像素，把它写进 RAM 的某个位置。
3. 同时从 RAM 读出一个「老像素」送到 `data_out`——这个老像素正是 1280 个有效像素之前写进来的，也就是**上一行同列**像素。
4. 下一行流到同一列时，本行像素又被写进同一位置，覆盖掉那行更老的值——RAM 始终只保留「最近一行」，不需要保存整帧。

> 资源视角：一块 `linemem` = 1280 × 8 bit ≈ 1.25 KB。`sharp_slice` 里级联 6 块，R/G/B 三通道各一个 `sharp_slice`，共 6 × 3 = 18 块行存储，这正是 u1-l3 提到的「约 16% 片上存储」的主要来源。

#### 4.1.3 源码精读

RAM 阵列的类型与信号声明（**1280 项、每项 0..255 的整数，即一个 8 位颜色通道字节**）：

[sharp_linemem.vhd:L20-L21](https://github.com/automatesolutions/FPGA_FIR-FILTER/blob/3f7aef90f4d34fa62f00ca72c260fc49c3c04a8c/FPGA-FIR-Filter-master/FPGA-Design/sharp_linemem.vhd#L20-L21) — 声明 `ram_array` 为 0..1279 的整数数组，`ram` 是这块存储。

端口的 `data_in` / `data_out` 也都是 `integer range 0 to 255`，与一个像素通道的字节宽度一致：

[sharp_linemem.vhd:L10-L16](https://github.com/automatesolutions/FPGA_FIR-FILTER/blob/3f7aef90f4d34fa62f00ca72c260fc49c3c04a8c/FPGA-FIR-Filter-master/FPGA-Design/sharp_linemem.vhd#L10-L16) — 模块对外只暴露 `clk / reset / write_en / data_in / data_out`，看起来像一个「延迟一行」的黑盒。

#### 4.1.4 代码实践

这是一个**源码阅读型实践**，目的是把「1280 ↔ 720p」对应关系钉死。

1. 实践目标：亲手算出行存储器的总位数，并解释为什么是 1280 而不是 720。
2. 操作步骤：
   - 打开 `sharp_linemem.vhd`，确认 `ram_array` 是 `array (0 to 1279)`，即 1280 项。
   - 回答：720p 的「720」指的是横向还是纵向？「1280」呢？
   - 计算：一块 `linemem` 存多少 bit？整个设计（18 块）共多少 bit？
3. 需要观察的现象：写出算式即可。
4. 预期结果：720 指纵向行数，1280 指每行有效像素数；RAM 深度取 1280 是为了「装下一整行」。单块 = 1280 × 8 = 10240 bit；18 块 ≈ 184320 bit（约 180 Kbit）。
5. 结论：若有人误以为「720p → RAM 该有 720 项」，那是因为把行数当成了每行像素数——本实践就是为了排除这个常见误解。

#### 4.1.5 小练习与答案

- **练习 1**：如果把视频格式从 720p 换成 1080p（1920×1080），`ram_array` 的深度应改成多少？
  - **答**：1920。1080p 每行有效像素是 1920，行存储器要装下一整行，故深度 = 1920。
- **练习 2**：RAM 项的类型是 `integer range 0 to 255`，为什么不是 `std_logic_vector(7 downto 0)`？
  - **答**：本设计在内部统一用 0..255 的整数表示一个像素通道（见顶层 `sharp.vhd` 的类型转换），用整数能让乘加表达式（`sharp_arith`）写得更直观；综合工具仍会把它映射成 8 位存储。

### 4.2 循环读写地址管理

#### 4.2.1 概念说明

有了 1280 项 RAM，下一个问题是：**怎么管理读写地址？**

最笨的办法是「移位寄存器」——每个时钟把全部 1280 项往后挪一格。这对 1280 项来说太费资源（每个像素都要 1280 个触发器）。

更聪明的办法是**循环缓冲（circular buffer）**：数据原地不动，只移动两个「地址指针」`wr_address`（写指针）和 `rd_address`（读指针）。写到尾就回到头上，像一条咬住自己尾巴的蛇。这样 1280 项可以用 RAM（而不是触发器）实现，资源代价小得多。

#### 4.2.2 核心流程

每个有效像素时钟（`write_en = '1'`）里做三件事，顺序很关键：

```
wait until rising_edge(clk);
if write_en = '1' then
    1) data_out <= ram(rd_address);     -- 先读：取出「老像素」
    2) ram(wr_address) <= data_in;      -- 后写：存入「新像素」
end if;
-- 然后推进两个指针（带回绕）：
if reset = '1' then
    wr_address := 0;  rd_address := 1;
elsif write_en = '1' then
    wr_address := rd_address;           -- 写指针跟随读指针
    if rd_address = 1279 then
        rd_address := 0;                -- 到尾回绕
    else
        rd_address := rd_address + 1;
    end if;
end if;
```

要点：

- **读改写（read-before-write）**：同一次时钟沿里，先用 `ram(rd_address)` 的**旧值**更新 `data_out`，再把 `data_in` 写进 `ram(wr_address)`。由于 VHDL 里信号赋值（`<=`）在进程挂起时才生效，`data_out` 拿到的是覆盖前的旧内容——这正是我们要的「上一行像素」。
- **回绕**：`rd_address` 走到 1279 后归 0，形成环形，永不越界。
- **写指针跟随读指针**：`wr_address := rd_address`，两个指针始终相邻。

> 复位初值 `wr=0, rd=1` 让两指针相差 1。一个推论：单独看一块 `linemem`，它的输出相对输入存在 1 个像素列的偏移。这个偏移在 `sharp_slice` 的级联里被「级间信号延迟」恰好抵消——后一级的 `data_in` 接的是前一级的 `data_out`（信号），比组合连线晚一拍，正好把列偏移拉回同一列，所以最终 `v_tap(0..6)` 仍覆盖同一列的 7 行（详见 u3-l3）。初读时抓住「延迟一行」这个功能即可，不必纠结这一格的偏移。

#### 4.2.4 代码实践

这是一个**纸笔推演型实践**，帮你把指针走向彻底看清（无需仿真器）。

1. 实践目标：手算 `linemem` 复位后头几个有效像素的指针值。
2. 操作步骤（假设把 1280 暂时想成 4，方便手算，逻辑完全一致）：
   - 复位后：`wr=0, rd=1`。
   - 第 1 个有效像素到达：先读 `ram(1)`、写 `ram(0)`；然后 `wr:=rd=1`，`rd:=2`。
   - 第 2 个：读 `ram(2)`、写 `ram(1)`；`wr:=2`，`rd:=3`。
   - 第 3 个：读 `ram(3)`、写 `ram(2)`；`wr:=3`，`rd:=0`（回绕）。
   - 第 4 个：读 `ram(0)`、写 `ram(3)`；`wr:=0`，`rd:=1`（回到起点）。
3. 需要观察的现象：4 拍之后指针回到 `(0,1)`，正好对应「写完一整行」。
4. 预期结果：把上面 4 行填成一张表（输入列号 / wr / rd / 读出地址 / 写入地址），验证回绕发生在「写完最后一列」之时。
5. 把缓冲深度换回 1280：同一逻辑在 1280 拍后回到起点，对应「写完一整行 720p 有效像素」。

#### 4.2.5 小练习与答案

- **练习 1**：为什么用「两个指针 + RAM」而不是「1280 级移位寄存器」？
  - **答**：移位寄存器每像素要 1280 个触发器，18 块就是几十万触发器，代价极高；RAM 用片上存储块实现，面积/功耗都低得多，地址指针只需几个寄存器。
- **练习 2**：把 `data_out <= ram(rd_address)` 和 `ram(wr_address) <= data_in` 互换顺序，结果会变吗？
  - **答**：不会。二者都是信号赋值（`<=`），在进程挂起时才一起生效；只要 `rd_address ≠ wr_address`，读到的都是旧值。顺序在代码里不影响语义。
- **练习 3**：如果 `rd_address` 和 `wr_address` 指向同一格，会发生什么？
  - **答**：读到的可能不再是「上一行」旧值，而是被本行新值覆盖后的值，延迟关系被破坏。本设计让两指针始终相差 1 来规避这一点。

### 4.3 写使能与行延迟

#### 4.3.1 概念说明

最后一个关键点：**为什么用 `de_in` 当写使能？**

真实的 720p 一行并非只有 1280 个时钟——按标准，一行总时长约 1650 个像素时钟，其中前 1280 个是有效像素，后 370 个是行消隐（blanking，`de=0`）。如果在消隐期也推进地址指针，那么「1280 项 = 一行」的对齐就会被消隐期打乱。

解决办法很优雅：**只在有效像素期（`de=1`）才读写、才推进指针**。消隐期指针原地不动。这样一来：

- 指针每行恰好推进 1280 次；
- 缓冲深度 1280 就精确对应「一行有效像素」；
- 每行起点指针自动回到同一位置，天然与「上一行同列」对齐，无需额外对齐逻辑。

这就是把 `write_en` 直接接 `de_in` 的根本原因。

#### 4.3.2 核心流程

把 `linemem` 放回 `sharp_slice` 的语境里看：

```
v_tap(0) <= data_in;                       -- 当前像素直接作为第 0 个抽头
for i in 0..5 generate
    linemem: write_en => de_in,            -- 只在有效像素期写
             data_in  => v_tap(i),
             data_out => v_tap(i+1);       -- 输出 = 一行前的同列像素
```

6 块级联后：`v_tap(0)` 是本行、`v_tap(1)` 是上一行、……、`v_tap(6)` 是上 6 行，全部同一列——7 个垂直抽头齐了。

`de_in` 同时承担两个角色（见 u3-l2）：它既是给后端对齐用的视频时序信号，又是行存储器的写使能。两路同源于顶层的 `de_0`。

#### 4.3.3 源码精读

在 `sharp_slice` 里，`generate` 把 6 块 `linemem` 级联，**`write_en` 端口统一接 `de_in`**：

[sharp_slice.vhd:L27-L36](https://github.com/automatesolutions/FPGA_FIR-FILTER/blob/3f7aef90f4d34fa62f00ca72c260fc49c3c04a8c/FPGA-FIR-Filter-master/FPGA-Design/sharp_slice.vhd#L27-L36) — `v_tap(0)<=data_in` 是组合连线；6 块 `linemem` 的 `write_en` 都映射到 `de_in`，构成垂直抽头链。

回到 `linemem` 内部，读写块和指针推进块**都受 `write_en` 门控**：

[sharp_linemem.vhd:L31-L46](https://github.com/automatesolutions/FPGA_FIR-FILTER/blob/3f7aef90f4d34fa62f00ca72c260fc49c3c04a8c/FPGA-FIR-Filter-master/FPGA-Design/sharp_linemem.vhd#L31-L46) — 两段 `if write_en='1'` 保证消隐期既不读写也不推进指针，从而「1280 项 = 一行有效像素」的等式恒成立。

#### 4.3.4 代码实践

这是本讲的核心动手任务（对应学习目标里的验证实验）。**需要 VHDL 仿真器**（ModelSim/GHDL/Aldec 等）；若无环境，可只做步骤 1–3 的预测，标注「待本地验证」。

1. 实践目标：把 `ram_array` 容量从 1280 改成 640，观察垂直方向出现的错位/重影，并解释为什么 1280 才对应 720p。
2. 操作步骤：
   - 复制一份 `sharp_linemem.vhd` 到你自己的实验目录（**不要改原始源码**）。
   - 把 `array (0 to 1279)` 改成 `array (0 to 639)`；同步把 `wr_address` / `rd_address` 的 `range 0 to 1279` 改成 `range 0 to 639`，把回绕判断 `rd_address = 1279` 改成 `rd_address = 639`。
   - 用 u5-l1 的 `sim_sharp.vhd` 跑一张 1280×720 的 PPM 测试图（注意把 testbench 里硬编码的路径改成你本地的相对路径）。
3. 需要观察的现象：输出图像在水平方向出现约半幅宽（约 640 像素）的错位/重影；若用 u5-l2 的自校验 testbench，`mismatch` 计数会大量大于 0。
4. 预期结果与解释：缓冲深度 \(D=640 < L=1280\) 时，读出的是 \(D\) 个有效像素之前写入的值——对第 \(c\) 列（\(c\ge 640\)）而言，那是**本行**第 \(c-640\) 列；对 \(c<640\)，则跨到了**上一行**。于是「垂直抽头」不再来自同一列的 7 行，垂直滤波被污染，画面出现重影。这正说明：**只有当 \(D\) 恰好等于一行有效像素数（720p 的 1280）时，「延迟一行」才成立**。
5. 恢复 1280 后重跑，自校验 testbench 应报告通过（`EVERYTHING OK`）——**待本地验证**。

> 提示：本实践会改源码，请只在副本上操作；本讲义禁止修改仓库原始源码。

#### 4.3.5 小练习与答案

- **练习 1**：如果把 `write_en` 恒接 `'1'`（不再用 `de_in` 门控），会出什么问题？
  - **答**：消隐期也会推进指针并读写。一行总长 1650 时钟 ≠ 1280，缓冲深度对不上一行，读出的不再是「上一行同列」，垂直抽头错位，图像会出现规律性条纹/错位。
- **练习 2**：为什么 `linemem` 的复位要把 `rd_address` 置成 1 而不是 0？
  - **答**：让 `wr` 与 `rd` 错开一格（`wr=0, rd=1`），避免读写撞在同一地址上，保证「读旧值、写新值」互不干扰（参见 4.2.5 练习 3）。
- **练习 3**：场消隐（垂直 blanking，连续多行 `de=0`）期间，行存储器会怎样？
  - **答**：`write_en=0`，指针冻结、不读写。新帧第一行到来时，指针仍在上一帧末尾的位置；由于每行指针都回到同一组位置，下一帧各行仍能与「上一行同列」正确对齐。

## 5. 综合实践

把本讲三个模块串起来，做一个**分辨率迁移设计**（纸笔 + 局部改代码，无需完整综合）：

> 假设要把本设计从 720p（1280×720）改成 1080p（1920×1080），`sharp_linemem` 需要怎么改？资源影响多大？

要求完成：

1. **容量**：计算新的 `ram_array` 深度，给出新的 `array (0 to ?)`、地址变量 `range`、回绕判断值。
2. **寻址**：说明 `wr/rd` 指针逻辑是否需要改动（结论应是不需要，只改深度相关常量）。
3. **写使能**：确认 `write_en => de_in` 这条映射是否仍成立（1080p 仍以 `de` 标记有效像素，结论是成立）。
4. **资源**：估算 18 块行存储的总 bit 数，与 720p 时对比，说明对 Cyclone V 片上存储占用的影响。
5. **联动**：想一想，除了 `sharp_linemem`，还有哪些地方会因为分辨率改变而需要调整（提示：u5 的 testbench 图像尺寸、u6-l2 的 SDC 时钟周期）。这条留作开放思考，不要求给出完整答案。

参考答案要点：深度改为 1920；地址范围改 `0 to 1919`、回绕判断改 `= 1919`；指针与写使能逻辑不变；单块 = 1920×8 = 15360 bit，18 块 ≈ 276480 bit（约 270 Kbit），比 720p 的约 180 Kbit 增加约 50%；testbench 需换成 1920×1080 的 PPM，SDC 时钟也要按 1080p 像素时钟（如 148.5 MHz）重设。

## 6. 本讲小结

- `sharp_linemem` 用一块 **1280 项 RAM** 把像素**延迟一行**；1280 = 720p 每行的有效像素数（注意 720p 的「720」是行数，每行有 1280 个像素）。
- 它用**循环缓冲**而非移位寄存器：两个地址指针 `wr_address` / `rd_address` 原地推进，到 1279 回绕，数据不动、只动指针，省下大量触发器。
- 关键的**读改写**时序：同一时钟沿先读 `ram(rd)` 的旧值到 `data_out`，再写 `data_in` 到 `ram(wr)`，从而在覆盖前救出「上一行」像素。
- `write_en = de_in` 让指针**只在有效像素期推进**，消隐期冻结，于是「1280 项 = 一行有效像素」恒成立，每行起点自动对齐上一行同列。
- 6 块级联 + 一根组合连线凑出 7 个同列垂直抽头 `v_tap(0..6)`，喂给 `sharp_arith` 做垂直滤波（详见 u3-l3）。
- 把缓冲深度改小（如 640）会破坏「延迟一行」，画面出现水平错位/重影——这是验证「为什么必须是 1280」最直接的方法。
