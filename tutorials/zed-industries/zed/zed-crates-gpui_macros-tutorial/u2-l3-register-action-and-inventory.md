# register_action 与 inventory：action 如何自动注册

## 1. 本讲目标

上一讲（u2-l2）我们在 `derive_action.rs` 的大模板里留下了一个悬念：`#registration` 片段排在 `impl gpui::Action` 之前，是整个 Action 体系里唯一「不属于 trait 实现」的生成代码。本讲就把它拆开，学完后你应该能：

1. 解释一个**从未被任何代码调用**的函数 `__autogenerated` 是如何完成 action 注册的。
2. 读懂 `generate_register_action` 生成的隐藏构建函数、`MacroActionBuilder` 函数指针与 `MacroActionData` 七个字段之间的关系。
3. 说清 `inventory::collect!` / `inventory::submit!` / `inventory::iter` 三件套如何在 `main` 之前把散落在各个 crate 里的 action 收集到一起。
4. 掌握 gpui 侧 `ActionRegistry` 的装载与查询 API：`build_action`、`build_action_type`、`all_action_names`、`generate_list_of_all_registered_actions`。
5. 逐行读懂 gpui 的 `actions!` 声明宏的两种形式，理解「声明宏包装派生宏」的两层架构。

## 2. 前置知识

本讲默认你已读过 u2-l1、u2-l2（`#[derive(Action)]` 的属性解析与代码生成）。在此之上需要几个新概念：

- **函数指针类型**：`fn(A) -> B` 不只是函数签名的写法，它本身是一个类型，可以当作值存进结构体字段。本讲的核心数据结构就是一个装函数指针的 struct。
- **`Self: Sized` 关联函数**（u2-l2 已铺垫）：`name_for_type()`、`build()` 等 trait 关联函数没有 `self`，只能通过具体类型调用（`Foo::build(v)`），也因此可以写成 `<Foo as gpui::Action>::build` 这样的**路径**——这正是把它们装进函数指针字段的前提。
- **`inventory` crate**：一个第三方「分布式注册」库（本仓库固定版本 `inventory = "0.3.19"`，见 [Cargo.toml:658](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/Cargo.toml#L658)）。它的卖点是：任何 crate 都能「提交」一个值，而**不需要任何人在 `main` 里写一行收集代码**。
- **`main` 之前的初始化**：C/C++ 程序有「在 `main` 前运行的构造函数」（GCC 的 `__attribute__((constructor))`、`.init_array` 段）。inventory 利用的正是这类链接器/启动钩子机制，让静态注册代码在程序入口前执行。具体实现是 inventory 的内部细节，本讲只讲它对使用者承诺的行为：`submit!` 提交的值在 `main` 前可用、`iter` 运行期可遍历。
- **声明宏与过程宏的分工**（u1-l2、u1-l3 已铺垫）：`macro_rules!` 擅长「按模式批量重复生成条目」，过程宏擅长「对单个类型做深度分析后生成实现」。`actions!` 与 `#[derive(Action)]` 正好各占一层。

## 4. 核心概念与源码讲解

本讲拆成四个最小模块：4.1 inventory 收集机制 → 4.2 宏生成的注册代码 → 4.3 gpui 的注册表 → 4.4 `actions!` 声明宏。它们正好构成一条数据的完整旅程。

### 4.1 inventory：main 之前的链接期收集机制

#### 4.1.1 概念说明

先想一个架构问题：Zed 仓库里有**上千个 action**，分散在 `editor`、`workspace`、`theme_selector` 等几十个 crate 里。keymap 需要按名字（如 `editor::MoveUp`）找到并构建任意一个 action。这意味着必须存在一个「全局注册表」。但：

- `main()` 不可能知道所有 action 的名字去逐个注册；
- 每个 action 所在的 crate 也不应该依赖某个中心 crate 去调用 `registry.insert(...)`——那样每写一个 action 都要多写一行注册代码，而且注册时机（`App` 何时创建？）很难统一。

`inventory` 解决的就是这类「分布式自注册」问题。它提供三个原语：

| 原语 | 调用位置 | 作用 |
| --- | --- | --- |
| `inventory::collect!(T)` | 定义 `T` 的 crate（gpui） | 声明「`T` 是可收集类型」，为它建立一条全局链表 |
| `inventory::submit! { T 的值 }` | 任意 crate、任意作用域 | 把一个值挂到 `T` 的链表上，无需任何人调用它 |
| `inventory::iter::<T>` | 任意运行期代码 | 遍历链表上所有已提交的值 |

关键在于 `submit!` 的实现方式：它把值打包进一个**静态节点**，并借助链接器支持的启动钩子让一段注册代码在 `main` 之前运行。所以 `submit!` 写在哪里、外层函数有没有被调用，都**不影响注册发生**——只要这个静态节点所在的目标文件被链接进了最终二进制。（`submit!` 的具体展开是 inventory 的内部实现，建议用 cargo expand 亲自观察，见 4.1.4。）

#### 4.1.2 核心流程

```text
编译期（每个 submit! 调用点）
  │  生成一个静态节点（内含值/生成值的代码）+ 一个启动函数
  ▼
链接期
  │  链接器把启动函数收进二进制的启动区（类比 .init_array）
  ▼
main 之前
  │  启动函数逐个执行：把节点挂到 T 的全局链表
  ▼
运行期（gpui 创建 App 时）
  │  inventory::iter::<T> 遍历链表 → ActionRegistry 建立索引
  ▼
按名字/按 TypeId 构建任意 action
```

一个重要推论：**收集范围 = 整个二进制**。测试二进制链接了哪些 crate，`inventory::iter` 就能看到哪些 action。所以在一个只依赖 gpui 的测试里，你能看到 gpui 自己的 action（如 `zed::NoAction`），却看不到 `editor` crate 的 action——它们根本没被链接进来。

#### 4.1.3 源码精读

gpui 侧的收集声明只有一行（[action.rs:282](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L282)）：

```rust
inventory::collect!(MacroActionBuilder);
```

这一行紧跟在 `MacroActionBuilder` 的定义之后，把该类型登记为可收集类型。gpui 对 inventory 的依赖声明在 [crates/gpui/Cargo.toml:64](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/Cargo.toml#L64)（`inventory.workspace = true`）。

再看宏生成代码里的调用（[register_action.rs:41-43](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/register_action.rs#L41-L43)）：

```rust
gpui::private::inventory::submit! {
    gpui::MacroActionBuilder(#action_builder_fn_name)
}
```

注意路径是 `gpui::private::inventory`，而不是 `inventory`。这是一个**依赖桥接**技巧：`gpui_macros` 是 `proc-macro = true` 的宏 crate（[gpui_macros/Cargo.toml:17](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/Cargo.toml#L17)），它生成的代码要**在用户 crate 里编译**，如果直接写 `inventory::submit!`，就要求每个用了 action 的业务 crate 都在自己的 `Cargo.toml` 里加 `inventory` 依赖。而 gpui 在 `private` 模块里把它再导出了出来（[gpui.rs:74-82](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/gpui.rs#L74-L82)）：

```rust
/// Do not touch, here be dragons for use by gpui_macros and such.
#[doc(hidden)]
pub mod private {
    pub use anyhow;
    pub use inventory;      // ← 就是它
    pub use schemars;
    pub use serde;
    pub use serde_json;
}
```

于是业务 crate 只需依赖 gpui 一个。这个模式与 u2-l2 讲过的 `gpui::private::serde_json` 完全同源——那是为了 `build` 方法里的 `serde_json::from_value`。模块名叫 `private` 又标 `#[doc(hidden)]`，意思是「这是给宏用的后门，人类代码别碰」。

#### 4.1.4 代码实践

**实践目标**：亲眼看到 `submit!` 展开后是静态项，而不是普通函数调用。

**操作步骤**：

1. 安装 cargo-expand（若未安装）：`cargo install cargo-expand`。
2. 在仓库根目录执行：`cargo expand -p gpui --test action_macros`。
3. 在输出中搜索 `__gpui_actions_builder_`（本讲 4.2 生成的函数名）与 `inventory`。

**需要观察的现象**：展开结果里 `inventory::submit!` 变成了一个包含 `static` 项与启动注册代码的块（具体形态由 inventory 0.3.19 决定），它出现在 `__autogenerated` 函数体内部，且没有任何地方调用 `__autogenerated`。

**预期结果**：你能指出「注册不依赖任何调用」的物证——静态项与启动钩子。`submit!` 的确切展开文本属于 inventory 内部实现，不同小版本可能不同，此步**待本地验证**。

#### 4.1.5 小练习与答案

**练习 1**：为什么 `inventory::collect!(MacroActionBuilder)` 写在 gpui 里，而 `submit!` 由宏生成在用户 crate 里？反过来行不行？

**答案**：`collect!` 建立「类型的收集链表」，必须与类型定义放在一起（由定义方声明「此类型可被分布式收集」）；`submit!` 则是每个具体 action 的贡献点，天然分散在各业务 crate。反过来（collect 在业务 crate、submit 在 gpui）没有意义：gpui 不知道也不该知道业务 crate 里有哪些 action 类型。

**练习 2**：在一个只依赖 gpui（不依赖 editor crate）的测试二进制里，`inventory::iter::<MacroActionBuilder>` 能看到 `editor::MoveUp` 吗？为什么？

**答案**：不能。inventory 的注册单元是静态节点，跟随目标文件链接。editor crate 没有被链接进这个测试二进制，其 `submit!` 生成的静态节点根本不存在于最终产物中。这也是为什么每个测试二进制各自独立收集，互相不串。

### 4.2 generate_register_action：隐藏函数与 MacroActionBuilder/MacroActionData

#### 4.2.1 概念说明

先看 gpui 侧定义的两个「桥」类型（[action.rs:264-280](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L264-L280)）：

```rust
/// This type must be public so that our macros can build it in other crates.
/// But this is an implementation detail and should not be used directly.
#[doc(hidden)]
pub struct MacroActionBuilder(pub fn() -> MacroActionData);

#[doc(hidden)]
pub struct MacroActionData {
    pub name: &'static str,
    pub type_id: TypeId,
    pub build: ActionBuilder,
    pub json_schema: fn(&mut schemars::SchemaGenerator) -> Option<schemars::Schema>,
    pub deprecated_aliases: &'static [&'static str],
    pub deprecation_message: Option<&'static str>,
    pub documentation: Option<&'static str>,
}
```

`MacroActionData` 是一个 action 的**注册名片**：名字、TypeId、构建函数、JSON schema 函数、弃用别名、弃用说明、文档——u2-l2 讲的 `impl Action` 九个方法里所有 `Self: Sized` 的关联函数都在这里有对应字段。

而 `MacroActionBuilder` 只有一个字段：**一个返回 `MacroActionData` 的函数指针**。为什么要多这一层间接？因为 `MacroActionData` 的字段不是常量表达式：

- `TypeId::of::<T>()` 在 stable Rust 上不能在常量上下文里求值；
- `name` 来自 `<T as gpui::Action>::name_for_type()` 函数调用；
- `deprecated_aliases()` 等同理。

也就是说，**名片必须靠运行代码才能造出来**。而 inventory 的提交值适合是一个零成本的纯常量——函数指针正好是（`<T as gpui::Action>::name_for_type` 这样的关联函数路径在编译期就是一个小常数）。所以注册时只交一个「知道怎么造名片的函数」，等 gpui 装载注册表时再统一调用 `builder.0()` 现场造名片（见 4.3）。

顺带解释注释里的两句英文：这两个类型「必须 pub」是因为宏要在**其他 crate** 里构造它们（生成代码运行在用户 crate 的命名空间）；「是实现细节，勿直接使用」则用 `#[doc(hidden)]` 落实。

#### 4.2.2 核心流程

`#[derive(Action)]`（或 `register_action!`）触发的注册代码生成全流程：

```text
derive_action.rs 解析完 #[action(...)] 属性
  │
  ├─ no_register 为 true？ ──► registration = quote! {}（什么都不生成）
  │
  └─ 否则 ──► generate_register_action(struct_name)
                  │
                  ├─ format_ident!：把类型名小写，拼出 __gpui_actions_builder_ 前缀的函数名
                  │
                  └─ 生成：
                        impl 类型名 {
                            fn __autogenerated() {          ← 从未被调用
                                fn __gpui_actions_builder_xxx() -> gpui::MacroActionData { ... }
                                gpui::private::inventory::submit! {
                                    gpui::MacroActionBuilder(__gpui_actions_builder_xxx)
                                }
                            }
                        }
```

这段代码被 `derive_action.rs` 放在 `impl gpui::Action` 之前一起输出（[derive_action.rs:156-164](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/derive_action.rs#L156-L164)）：

```rust
let registration = if no_register {
    quote! {}
} else {
    generate_register_action(struct_name)
};

TokenStream::from(quote! {
    #registration

    impl gpui::Action for #struct_name {
```

这也回收了 u2-l2 埋下的伏笔：`#[action(no_register)]` 的唯一作用就是让这里生成空片段——trait 实现照常生成，只是不进入全局注册表（适合「只被代码直接构造、永不被 keymap 按名调用」的 action）。

#### 4.2.3 源码精读

整个文件只有两个函数。第一个是 `#[proc_macro]` 入口（[register_action.rs:6-13](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/register_action.rs#L6-L13)）：

```rust
pub(crate) fn register_action(ident: TokenStream) -> TokenStream {
    let name = parse_macro_input!(ident as Ident);
    let registration = generate_register_action(&name);
    ...
}
```

它是函数式过程宏 `register_action!(Paste)` 的实现（入口声明在 [gpui_macros.rs:24-30](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/gpui_macros.rs#L24-L30)，再导出于 [gpui.rs:109-111](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/gpui.rs#L109-L111)）。输入只解析出一个标识符——这是全 crate 输入最简单的宏。它面向「想手动 `impl gpui::Action` 又想进注册表」的场景，trait 文档给了完整示例（[action.rs:92-116](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L92-L116)）：手写完 `impl Action for Paste {...}` 后跟一句 `register_action!(Paste);` 即可。

第二个是核心生成器（[register_action.rs:15-47](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/register_action.rs#L15-L47)）。逐段看：

**函数名生成**（[register_action.rs:16-19](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/register_action.rs#L16-L19)）：

```rust
let action_builder_fn_name = format_ident!(
    "__gpui_actions_builder_{}",
    type_name.to_string().to_lowercase()
);
```

`format_ident!`（quote 提供）把 `SelectNext` 变成 `__gpui_actions_builder_selectnext`。小写化只是让生成名更「机器味」，即便两个不同类型小写后撞名也无妨——这个函数只存在于各自 `__autogenerated` 的函数体作用域内，天然隔离。

**生成体**（[register_action.rs:21-46](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/register_action.rs#L21-L46)）：

```rust
impl #type_name {
    /// This is an auto generated function, do not use.
    #[automatically_derived]
    #[doc(hidden)]
    fn __autogenerated() {
        #[doc(hidden)]
        fn #action_builder_fn_name() -> gpui::MacroActionData {
            gpui::MacroActionData {
                name: <#type_name as gpui::Action>::name_for_type(),
                type_id: ::std::any::TypeId::of::<#type_name>(),
                build: <#type_name as gpui::Action>::build,
                json_schema: <#type_name as gpui::Action>::action_json_schema,
                deprecated_aliases: <#type_name as gpui::Action>::deprecated_aliases(),
                deprecation_message: <#type_name as gpui::Action>::deprecation_message(),
                documentation: <#type_name as gpui::Action>::documentation(),
            }
        }

        gpui::private::inventory::submit! {
            gpui::MacroActionBuilder(#action_builder_fn_name)
        }
    }
}
```

四个值得精读的点：

1. **`impl #type_name { fn __autogenerated() }` 的包裹**。派生宏的输出会被追加到用户模块的顶层作用域。如果把构建函数和 `submit!` 直接铺在模块顶层，会在用户模块的命名空间里引入 `__gpui_actions_builder_*` 等名字，有与用户自身条目撞名的风险。包进一个 impl 块的**方法体**之后，所有嵌套条目（构建函数、静态节点）的作用域都被限制在函数体内，用户命名空间零污染。而这个方法本身永远不会被调用——它只是一层「命名空间保险箱」，注册靠的是 `submit!` 展开出的静态项与启动钩子，与控制流无关。`#[automatically_derived]` 标记这是生成代码（让编译器/lint 放宽对它的检查），`#[doc(hidden)]` 与两层 "do not use" 注释双保险。
2. **七个字段全部用关联函数路径填充**。`<#type_name as gpui::Action>::name_for_type()` 等在编译期就是常量般的函数项，`build` 与 `json_schema` 更是直接把关联函数**当作函数指针**写进字段。这回应了 4.2.1 的间接层设计：名片在函数体里「现场制造」，函数本身可以原样提交给 inventory。
3. **`::std::any::TypeId::of::<#type_name>()`** 用全路径写法，呼应 u1-l2 讲过的「生成代码不假定用户模块里有任何 use」。
4. **`#action_builder_fn_name` 不带 `()`**：`MacroActionBuilder` 的字段是函数指针，这里传的是函数**本身**（函数项自动协变为 `fn()` 指针），不是调用结果。

对照表——名片字段与 u2-l2 的 trait 方法一一对应：

| MacroActionData 字段 | 来源（Action 关联函数） | u2-l2 讲到的生成分支 |
| --- | --- | --- |
| `name: &'static str` | `name_for_type()` | namespace/name 拼接规则 |
| `type_id: TypeId` | `TypeId::of::<T>()`（非 trait 方法） | —— |
| `build` | `build` | no_json / 单元结构体 / serde 三分支 |
| `json_schema` | `action_json_schema` | no_json 与单元结构体返回 `None` |
| `deprecated_aliases` | `deprecated_aliases()` | `&[]` 或字符串切片 |
| `deprecation_message` | `deprecation_message()` | `#[action(deprecated = "...")]` |
| `documentation` | `documentation()` | doc 注释拼接 |

其中 `build` 字段的类型 `ActionBuilder` 是一个类型别名（[action.rs:231](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L231)）：

```rust
type ActionBuilder = fn(json: serde_json::Value) -> anyhow::Result<Box<dyn Action>>;
```

这正是 u2-l2 末尾提到的「函数指针桥接」：`build` 是 `Self: Sized` 关联函数，无法通过 `dyn Action` 调用；注册表把它抽成裸函数指针后，就能在只知道名字的情况下构建具体 action。

#### 4.2.4 代码实践

**实践目标**：在真实展开结果里定位 4.2.3 分析的每一个生成物。

**操作步骤**：

#### 4.2.5 小练习与答案

**练习 1**：为什么不直接 `inventory::submit! { MacroActionData { ... } }`，而要套一层函数指针？

**答案**：`MacroActionData` 的字段值（`TypeId::of::<T>()`、`name_for_type()` 的返回值等）需要**运行代码**才能得到，无法作为 inventory 静态节点的常量内容装配；而函数指针 `<T as gpui::Action>::name_for_type` 编译期即确定。提交「造名片的函数」、装载时再调用 `builder.0()`，同时满足了 inventory 的静态提交要求与名片的运行期构造需求。

**练习 2**：`__autogenerated` 从未被调用，为什么注册依然生效？如果把它放进一个真正被调用的函数里，行为会变吗？

**答案**：注册生效靠的是 `submit!` 展开出的静态节点与启动钩子（在 `main` 前由链接器安排执行），与 `__autogenerated` 是否被调用完全无关；函数体只是这些静态条目的词法容器。放进哪个函数都一样，甚至放进永远不会执行的分支里也一样——这也是 [action_macros.rs:8-15](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/tests/action_macros.rs#L8-L15) 敢把 `actions!` 写在测试函数体内部的原因。

**练习 3**：`#[action(no_register)]` 的 action 还能用 `Action::build` / `partial_eq` 吗？

**答案**：能。`no_register` 只让 `registration` 生成空片段（[derive_action.rs:156-158](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/derive_action.rs#L156-L158)），`impl gpui::Action` 照常生成，代码里可以直接 `Foo::build(json!({}))`。它失去的只是「被 keymap 按名字调用」的能力——因为注册表里没有它。

### 4.3 ActionRegistry：装载、查重与按名/按类型构建

#### 4.3.1 概念说明

inventory 链表是「无序的全量流水」，查询效率低（线性遍历）也不支持查重。gpui 在每个 `App` 里建一个真正的注册表 `ActionRegistry`：创建 `App` 时把链表一次性装载成若干 HashMap 索引，之后按名字/按 TypeId 构建就都是 O(1) 查表加一次函数指针调用。

#### 4.3.2 核心流程

```text
App::new（含每个 #[gpui::test] 创建的测试 App）
  │  app.rs:809  actions: Rc::new(ActionRegistry::default())
  ▼
ActionRegistry::default()          (action.rs:242-257)
  │  调用 load_actions()
  ▼
load_actions                        (action.rs:284-291)
  │  for builder in inventory::iter::<MacroActionBuilder>:
  │      let action = builder.0();      ← 现场调用 4.2 的构建函数，造出名片
  │      insert_action(action)
  ▼
insert_action                       (action.rs:293-333)
  ├─ 名字已存在？──► panic（action.rs:295-300）
  ├─ by_name[name] = ActionData { build, json_schema }
  ├─ 每个 deprecated_alias 同样进 by_name，并记录 别名→正名 映射
  ├─ names_by_type_id[TypeId] = name
  ├─ all_names.push(...)
  ├─ deprecation_messages[name] = msg（若有）
  └─ documentation[name] = doc（若有）
```

之后所有查询都走这张表：`build_action("editor::MoveUp", params)` 按名字构建；`build_action_type(&TypeId::of::<T>())` 先查 `names_by_type_id` 拿名字再构建。

#### 4.3.3 源码精读

**App 如何持有注册表**：`App` 结构体有字段 `pub(crate) actions: Rc<ActionRegistry>`（[app.rs:687](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/app.rs#L687)），在构造 `AppCell` 时初始化（[app.rs:802-809](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/app.rs#L802-L809)）：

```rust
actions: Rc::new(ActionRegistry::default()),
```

`ActionRegistry::default()` 里那句 `this.load_actions()`（[action.rs:253](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L253)）就是装载入口。**每个 `App` 都重新装载一遍**——包括每个测试创建的 App，而 inventory 链表是每个二进制一份，所以同一二进制里所有 App 看到同一套 action。

**装载循环**（[action.rs:284-291](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L284-L291)）：

```rust
pub(crate) fn load_actions(&mut self) {
    for builder in inventory::iter::<MacroActionBuilder> {
        let action = builder.0();
        self.insert_action(action);
    }
}
```

`builder.0()` 就是 4.2 里提交的那个函数指针的调用点——「名片」在这里才被造出来。

**注册表结构与查重**（[action.rs:233-240](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L233-L240)、[action.rs:259-262](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L259-L262)）：五张表 + 一个静态切片容器。`insert_action` 的第一件事就是查重（[action.rs:293-300](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L293-L300)），重名直接 panic，错误文案还提示了另一种撞名来源——弃用别名。这与 trait 文档的承诺一致（[action.rs:53](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L53)）：「Registering the actions with the same name will result in a panic during `App` creation.」因为装载发生在 `App` 构造时，重复注册的报错时机就是「创建 App 的那一刻」，这在测试里通常表现为整个测试二进制里任何测试一跑就崩。

**弃用别名**（[action.rs:308-324](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L308-L324)）：每个别名也插入 `by_name`（指向同一个构建函数），这样旧名字仍能触发 action；同时 `deprecated_aliases` 表记录「别名 → 正名」，供 UI 提示迁移。别名撞上已注册名同样 panic。

**两个查询入口**：

- `build_action(name, params)`（[action.rs:351-369](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L351-L369)）——查表拿函数指针，注意这一行：`(build_action)(params.unwrap_or_else(|| json!({})))`。keymap 里没写参数的 action 会以空 JSON 对象 `{}` 传入，这解释了 u2-l2 `build` 三分支里单元结构体为什么可以无视入参直接 `Ok(Box::new(Self))`。错误被包装成 `ActionBuildError::{NotFound, BuildError}`（定义于 [action.rs:190-229](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L190-L229)），`NotFound` 的文案 `"Didn't find an action named \"{name}\""` 你在 Zed 里配错 keymap 时大概率见过。
- `build_action_type(type_id)`（[action.rs:336-343](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L336-L343)）——反向入口：手上有类型（如 `TypeId::of::<editor::MoveUp>()`）想知道/构建它的 action。真实消费者在按键派发链路上：[key_dispatch.rs:372](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/key_dispatch.rs#L372) 与 [window.rs:5830](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/window.rs#L5830) 都调用它，把「绑定表里记录的类型」还原成可派发的 action 实例。

**对用户的门面**：`App::build_action`（[app.rs:2266-2273](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/app.rs#L2266-L2273)）与 `App::all_action_names`（[app.rs:2275-2279](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/app.rs#L2275-L2279)）都是对 `self.actions` 的一行转发。`all_action_names` 的文档注释特意澄清：「注册只服务于按名动态构建，与在元素树上绑定 action 无关」——`on_action` 监听的是类型，注册表只管 keymap 的字符串世界。

**不经 App 的全量清单**（[action.rs:415-423](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L415-L423)）：

```rust
pub fn generate_list_of_all_registered_actions() -> impl Iterator<Item = MacroActionData> {
    inventory::iter::<MacroActionBuilder>
        .into_iter()
        .map(|builder| builder.0())
}
```

它绕过 `ActionRegistry` 直接迭代 inventory，供「不需要 App 实例」的场景使用——最大的消费者是 Zed 的动作文档/schema 生成器：[zed/src/main.rs:1981-1994](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/zed/src/main.rs#L1981-L1994) 用它把每个 action 的名字、JSON schema、别名、弃用说明、文档汇成一份 JSON 输出。keymap 编辑器的 schema 校验（如 [keymap_file.rs:609](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/settings/src/keymap_file.rs#L609) 经由 `App::action_schemas`）则走注册表的 `action_schemas`（[action.rs:375-390](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L375-L390)）。

#### 4.3.4 代码实践

**实践目标**：走通「TypeId → 名字 → 构建」的反向链路，体会 `build_action_type` 为什么存在。

**操作步骤**：

1. 打开 [action.rs:336-343](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L336-L343)，确认它只是「查 `names_by_type_id` 拿名字，再调 `build_action(name, None)`」。
2. 打开 [window.rs:5830](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/window.rs#L5830)，往上看约 30 行，找到这次构建结果被用于什么（按键匹配后的 action 派发）。
3. 回答：为什么派发链路不直接 `Foo::build(...)` 而要绕注册表？

**需要观察的现象**：绑定表（keymap）存储的是 action 的**名字或 TypeId** 而非实例；真正派发那一刻才构建实例。

**预期结果**：因为 keymap 条目来自 JSON（只有字符串名字），而元素树上的监听器按类型注册——两个世界之间需要「名字 ↔ TypeId ↔ 实例」三向桥梁，`ActionRegistry` 的两张索引表加上 `build` 函数指针正是这座桥。本实践为纯阅读型。

#### 4.3.5 小练习与答案

**练习 1**：两个不同 crate 里各自用 `actions!(editor, [MoveUp])` 定义了同名 action，编译能过吗？什么时候报错？

**答案**：能编译——注册是静态提交，互不知晓。报错发生在**创建 `App` 时**：`insert_action`（[action.rs:295-300](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L295-L300)）发现 `by_name` 已有 `editor::MoveUp` 就 panic。这正是文档（[action.rs:53](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L53)）所说「panic during `App` creation」的典型场景。

**练习 2**：`build_action` 为什么把「没传参数」补成 `json!({})` 而不是 `Value::Null`？

**答案**：`build` 的 serde 分支走 `serde_json::from_value::<Self>`，单元结构体分支则无视入参，所以 `{}` 与 `Null` 对单元 action 都能成功；但对带字段 action，`{}` 是「空对象」，配合 `#[serde(default)]` 字段还能构造成功，而 `Null` 在 serde 语义中不是对象、必然反序列化失败。补 `{}` 让「keymap 不写参数」尽量等价于「传空对象」，行为最宽松一致。trait 文档（[action.rs:132-133](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L132-L133)）也明确写了「A value of `{}` will be passed for actions that don't have any parameters」。

**练习 3**：`ActionRegistry` 每个 `App` 建一份会不会浪费？上千个 action 每次建 App 都要重新 `builder.0()` 并插表。

**答案**：有一定成本，但发生在 `App::new`（通常整个进程一次；测试里每个测试函数一次），相对于进程生命周期可以忽略；换来的是实现极其简单——不需要全局单例、不需要考虑「谁先初始化」的顺序问题，测试之间也天然隔离（每个测试 App 都能拿到同一份完整清单，因为链表按二进制共享）。这是一种典型的「用启动时小成本换架构简单」的取舍。

### 4.4 actions! 声明宏：两种形式与两层架构

#### 4.4.1 概念说明

到目前为止我们讲的都是「给一个结构体生成注册代码」。但 Zed 里九成 action 是无字段的单元结构体，逐个写 `#[derive(...)]` 太啰嗦。gpui 的答案是 `actions!` 声明宏（[action.rs:23-40](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L23-L40)）：一条语句批量生成一串带 `#[derive(gpui::Action)]` 的单元结构体。

这就是 u1-l3 提过的「声明宏包装过程宏」两层架构：

- **外层 `macro_rules!`**：擅长模式重复——把 `[MoveUp, MoveDown, ...]` 展开成 N 个结构体；
- **内层 `#[derive(Action)]`**：擅长逐类型生成——为每个结构体生成 `impl Action` 与注册代码。

外层完全不理解 Action 语义，只做文本级组装；内层才是本单元两讲分析的主角。

#### 4.4.2 核心流程

```text
actions!(editor, [MoveUp, MoveDown])
  │  对每个 $name 展开（L25-32）：
  ▼
#[derive(::std::clone::Clone, ::std::cmp::PartialEq, ::std::default::Default,
         ::std::fmt::Debug, gpui::Action)]
#[action(namespace = editor)]
pub struct MoveUp;
  │  #[derive(gpui::Action)] 接管（u2-l1 + u2-l2 + 本讲 4.2）
  ▼
impl gpui::Action for MoveUp { ... }
+ impl MoveUp { fn __autogenerated() { ... inventory::submit! ... } }
  │  main 之前
  ▼
ActionRegistry 里出现 "editor::MoveUp"
```

#### 4.4.3 源码精读

宏定义本体（[action.rs:23-40](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L23-L40)，`#[macro_export]` 使之以 `gpui::actions` 的路径对所有下游 crate 可用）：

```rust
#[macro_export]
macro_rules! actions {
    ($namespace:path, [ $( $(#[$attr:meta])* $name:ident),* $(,)? ]) => {
        $(
            #[derive(::std::clone::Clone, ::std::cmp::PartialEq, ::std::default::Default, ::std::fmt::Debug, gpui::Action)]
            #[action(namespace = $namespace)]
            $(#[$attr])*
            pub struct $name;
        )*
    };
    ([ $( $(#[$attr:meta])* $name:ident),* $(,)? ]) => {
        $(
            #[derive(::std::clone::Clone, ::std::cmp::PartialEq, ::std::default::Default, ::std::fmt::Debug, gpui::Action)]
            $(#[$attr])*
            pub struct $name;
        )*
    };
}
```

逐个拆解设计点：

1. **两种形式**。第一种带 `$namespace:path` 前缀，生成 `#[action(namespace = $namespace)]`，action 名字是 `namespace::Name`；第二种直接给列表，没有 `#[action]` 属性，名字回退为裸结构体名（u2-l1 的缺省规则）。文档（[action.rs:22](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L22)）说明 namespace 可以省略、「但在 Zed 中是必需的」——Zed 的 keymap 一律用 `editor::MoveUp` 这样的全名。
2. **`$(,)?` 封尾逗号**：允许（也兼容）`[A, B,]` 末尾逗号，纯人体工学。
3. **`$(#[$attr:meta])*` 属性透传**：每个名字前面可以挂任意属性。最常见的是 doc 注释——[action_macros.rs:10-14](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/tests/action_macros.rs#L10-L14) 里的 `/// Documented action` 会落在 `SomeActionWithDocs` 上，被 u2-l1 讲过的 doc 提取逻辑收进 `documentation()`，最终出现在 Zed 的命令面板文档里。理论上也可以透传 `#[action(name = "...")]` 等属性（与外层生成的 `#[action(namespace = ...)]` 是两个独立属性，derive 会逐个解析、不冲突），但这属于冷门用法，**待本地验证**。
4. **全路径 derive**：`::std::clone::Clone` 等写法保证宏在任意模块展开都能解析，不需要调用方 `use` 任何东西——与 u1-l2 讲的「生成代码写全路径」同一原则，只是这次用在声明宏里。`gpui::Action` 则依赖 2018 版路径解析（依赖名即路径根），任何依赖 gpui 的 crate 都天然可用。
5. **derive 清单即使用契约**：`Clone + PartialEq + Default + Debug + gpui::Action`。前两个是 u2-l2 分析过的硬前提（`boxed_clone` 需要 `Clone`，`partial_eq` 需要 `PartialEq`），`Default`/`Debug` 是顺手附赠的便利。

宏的使用文档就在它上方（[action.rs:11-22](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L11-L22)），给出的示例 `actions!(editor, [MoveUp, MoveDown, MoveLeft, MoveRight, Newline])` 生成的名字正是 `editor::MoveUp` 等。

最后看 gpui 自己如何「自举」——文件底部的 `no_action` 模块（[action.rs:425-458](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L425-L458)）用 `actions!(zed, [NoAction])` 定义了解绑标记 action，又用带字段的 derive 定义了 `Unbind`。这验证了两层架构闭环：gpui 不需要任何特殊通道，它自己也是 `actions!` 与 `#[derive(Action)]` 的普通用户（注意 [action.rs:426](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L426) 的 `use crate as gpui;` 别名——u2-l2 讲过的「gpui 名字可用」前提在 gpui 内部靠它成立）。

**实践目标**：亲手追踪一次两层展开。

**操作步骤**：

#### 4.4.5 小练习与答案

**练习 1**：为什么 `actions!` 用声明宏实现，而不是也做成过程宏？

**答案**：它的工作纯粹是「把名字列表变成一串结构体定义」——没有类型分析、没有属性语义解析，`macro_rules!` 的重复模式就是为此而生，且声明宏无需 `proc-macro` crate、可导出为普通宏路径（`#[macro_export]`）。一旦落到「为某个结构体生成 impl」这种需要理解类型的活，才轮到过程宏。两层各自用在最擅长的地方。

**练习 2**：`actions!(editor, [MoveUp])` 和手写 `#[derive(..., gpui::Action)] #[action(namespace = editor)] pub struct MoveUp;` 有任何运行期差别吗？

**答案**：没有。前者只是后者的批量缩写，展开产物逐 token 等价（derive 清单、属性、结构体形态都一致）。差别只在写法密度：五个 action 一行搞定。

**练习 3**：`actions!` 的无 namespace 形式生成的 action，名字是什么？在 Zed 里能用吗？

**答案**：名字就是裸结构体名（如 `"MoveUp"`），因为缺省回退规则（u2-l1）在起作用。技术上能注册、能构建；但 Zed 约定所有 action 必须带 namespace（[action.rs:22](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L22)），无 namespace 形式主要服务于 gpui 层面的通用类型与测试。

## 5. 综合实践

把本讲四条线（宏生成 → inventory 收集 → 注册表装载 → 按名构建）串成一个可运行的验证实验。

**实践目标**：自己注册 action，并从「inventory 链表」和「App 注册表」两个视角分别验证它们可用。

**操作步骤**：

1. 先精读两个函数：`build_action_type`（[action.rs:336-343](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L336-L343)）与 `generate_list_of_all_registered_actions`（[action.rs:415-423](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L415-L423)），确认后者逐个调用 `builder.0()`。
2. 在本地克隆里新增一个集成测试文件 `crates/gpui/tests/action_registry_practice.rs`（只是练习用，验证后可删除），写入以下内容（示例代码，非仓库原有）：

```rust
use gpui::{actions, App};

// 第一个注册点：声明宏批量生成两个单元 action，名字将是
// "practice::FirstAction"、"practice::SecondAction"
actions!(practice, [FirstAction, SecondAction]);

#[gpui::test]
fn custom_actions_are_registered(cx: &mut App) {
    // 视角一：不经 App，直接迭代 inventory 链表
    let names: Vec<&'static str> = gpui::generate_list_of_all_registered_actions()
        .map(|data| data.name)
        .collect();
    assert!(names.contains(&"practice::FirstAction"));
    assert!(names.contains(&"practice::SecondAction"));

    // 同一迭代器里还能现场调用 build 函数指针
    for data in gpui::generate_list_of_all_registered_actions() {
        if data.name == "practice::FirstAction" {
            let built = (data.build)(serde_json::json!({})).unwrap();
            assert_eq!(built.name(), "practice::FirstAction");
        }
    }

    // 视角二：通过 App 的注册表（App 构造时已装载 inventory）
    let names = cx.all_action_names();
    assert!(names.contains(&"practice::FirstAction"));
    assert!(names.contains(&"practice::SecondAction"));

    let built = cx.build_action("practice::SecondAction", None).unwrap();
    assert_eq!(built.name(), "practice::SecondAction");
}
```

3. 运行：`cargo test -p gpui --test action_registry_practice`。

**需要观察的现象**：

- 两个视角都能看到你的 action——证明「`submit!` 静态注册 → 链表 → 注册表」整条链路对自定义 action 生效；
- `names` 里还混着 gpui 自己的 action（如 `zed::NoAction`、`zed::Unbind`，来自 [action.rs:425-458](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L425-L458) 的 `no_action` 模块）——印证「收集范围 = 整个测试二进制链接的所有 crate」；
- 若把 `actions!` 的 namespace 改成与另一个测试里已注册的名字冲突（例如同一文件里再写一个 `actions!(practice, [FirstAction])`），测试会在 App 创建时 panic——亲手复现 [action.rs:295-300](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs#L295-L300) 的查重。

**预期结果**：测试通过，断言全部成立。两点说明：`#[gpui::test]` 展开成普通 `#[test]` 并经 `gpui::run_test` 创建测试 App（生成逻辑见 [crates/gpui_macros/src/test.rs:185-209](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/test.rs#L185-L209)，细节是单元四的主题）；本实践在我这里未实际运行，**待本地验证**。

**进阶（可选）**：仿照 [action_macros.rs:17-20](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/tests/action_macros.rs#L17-L20) 再派生一个带 `count: usize` 字段的 action（需要 `serde::Deserialize` 与 `schemars::JsonSchema`），然后用 `cx.build_action("practice::ThirdAction", Some(serde_json::json!({"count": 7})))` 构建并断言 `partial_eq(&ThirdAction { count: 7 })` 为真——完整复现「keymap JSON → action 实例」的运行期链路。

## 6. 本讲小结

- 注册代码由 `generate_register_action`（[register_action.rs:15-47](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/register_action.rs#L15-L47)）生成：一个永不调用的 `__autogenerated` 方法里嵌着构建函数与 `inventory::submit!`，靠静态节点 + 启动钩子在 `main` 前完成注册，与控制流无关。
- 提交给 inventory 的是 `MacroActionBuilder`（装 `fn() -> MacroActionData` 函数指针），而不是数据本身——因为名片里的 `TypeId::of::<T>()` 等字段非常量，必须延迟到装载时用 `builder.0()` 现场构造。
- 宏生成代码统一走 `gpui::private::inventory`（[gpui.rs:74-82](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/gpui.rs#L74-L82)）再导出路径，业务 crate 因此无需直接依赖 inventory。
- gpui 在每个 `App` 构造时用 `ActionRegistry::default()` 把链表装载成 HashMap 索引：重名/别名冲突在此时 panic；`build_action`（按名字）与 `build_action_type`（按 TypeId）共用 `build` 函数指针完成实例化；`generate_list_of_all_registered_actions` 提供不经 App 的全量清单，供 Zed 生成动作文档与 keymap schema。
- `actions!` 是「声明宏包装派生宏」的外层：两种形式（带/不带 namespace）批量展开出带 `#[derive(gpui::Action)]` 的单元结构体，支持逐名字挂 doc 等属性；`register_action!` 则是手动实现 `Action` 时的裸注册入口，两者共享同一个生成器。

## 7. 下一步学习建议

本讲补完了 `#[derive(Action)]` 的最后一块拼图，单元二的 Action 部分到此收束。下一讲 u2-l4 转向 crate 中**代码量最少**的两个派生宏 `#[derive(IntoElement)]` 与 `#[derive(Render)]`，它们与 Action 派生形成鲜明对比：没有属性解析、没有注册机制，但会引入 Action 派生回避的问题——泛型处理（`split_for_impl`）。建议阅读顺序：

1. [derive_into_element.rs](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/src/derive_into_element.rs) 与 [render_test.rs](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui_macros/tests/render_test.rs)——为 u2-l4 做准备。
2. 想加深本讲理解的话，通读 [action.rs](https://github.com/zed-industries/zed/blob/fe9556a11e9cc9dbc78686041aa524d6932879db/crates/gpui/src/action.rs) 全文件（不到 460 行）——本讲只精读了注册相关的一半，前半的 trait 文档本身就是最好的用户手册。
3. 对「main 前注册」话题意犹未尽的读者，可以关注 inventory crate 的公开文档与 `ctor` 模式——它们在 Rust 生态里广泛用于插件注册、测试收集等场景。
