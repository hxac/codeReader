本讲覆盖 lsp crate 出站通知链路的三个模块：`notify` 类型化发送口、`NotificationSerializer` 延迟序列化、`new_internal` 的后台序列化任务。通知无 id 无响应，故 `notify` 是同步方法，返回 `Result<()>` 仅反映入队成败，唯一失败原因是通道已关闭。泛型 `T` 经 lsp-types 的 `notification::Notification` trait（关联常量 `METHOD`、关联类型 `Params`）在编译期绑定方法名与参数类型，入站 `on_notification::<T>` 用同一常量查表，收发对齐。`NotificationSerializer` 装的是 `FnOnce() -> String` 序列化闭包而非字符串，`serde_json::to_string` 被推迟到后台线程，前台调用只付入队代价。数据流两级串联：notification 通道（闭包）经单消费者任务转投 outbound 通道（String）再写 stdin，同线程多次 notify 保序；`request` 在调用点直发 outbound，其 `$/cancelRequest` 取消却走序列化路径。关闭级联：入队 Exit → 关 notification 通道 → 排空后关 outbound → flush 后 barrier 点亮 → kill 子进程，先入队再关闭不可颠倒。实践仿照 `register_buffer` 封装 didChangeConfiguration helper，用 `FakeLanguageServer` 端到端验收。
