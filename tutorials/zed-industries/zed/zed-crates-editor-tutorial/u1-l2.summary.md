本讲围绕 editor crate 的测试基建展开四个模块：测试开关三层设计、src/test.rs 公共工具箱、editor_tests.rs 组织方式、精读 test_undo_redo_with_selection_restoration。核心结论:`test-support` feature 是面向下游的总开关(转发 8 个依赖的 feature、启用 tree-sitter/proptest/unindent 等可选依赖),`[dev-dependencies]` 保证 editor 自测可用,源码用 `#[cfg(any(test, feature = "test-support"))]` 同时放行自测与下游复用两条路,故 `cargo test -p editor` 无需 `--features test-support`;`#[cfg(test)] mod editor_tests`(纯私有)与可导出的 `pub mod test` 的对比是理解关键。关键术语:marked text(`|` 表光标、`«»` 表选区)、`build_editor`/`select_ranges`/`assert_text_with_selections` 工具链、`#[gpui::test]` 与 `TestAppContext`、`init_test`(字体、设置、主题、release channel、editor 全局注册、日志六件套,测试世界的开机键)、事务分组(group_interval)、撤销恢复选区、跨编辑器事务不合并。editor_tests.rs 约 4.3 万行、507 处 `#[gpui::test]`、仅 3 个顶格 `#[test]`。方法论:「运行→改断言→读失败输出→git restore 还原」是后续讲义通用实验手段;marked text 与事务机制将分别由坐标管线(第 3 单元)与编辑事务(第 4 单元)讲义承接。
