本讲把 ChaCha20-Poly1305 设计从 PipelineC 的 C 版（`pipelinec_build`）移植到 Pypeline（PipelineC 的 Python 前端，`pypeline_build`），并借此修正两件事。一是接线改造：用「普通函数调用即例化子模块」取代 C 版的「全局 `Wire` + 多个 `@MAIN`」，引入 `Feedback[T]`（同一拍先读后写的组合反向信号，表达反压 ready）、`@interface` 端口（握手拆正反两半、同名加 `_if` 后缀）、接口函数（只手写正向、反向接线由 pass 自动生成）三项概念；唯一保留 `@MAIN`+Wire 的是真正被加密解密共享、带仲裁的 `chacha20_pipeline_shared`。二是修掉 C 版 Poly1305 的三处 limb 数学 bug：64×64 乘积截断成 `uint64_t`（改用 `uint128_t` 承接全乘积并进位）、模运算掩码误写为 42 位的 `0x3FFFFFFFFFF`（因 2^130 是 limb 2 的第 2 位，应为 `0x3`）、直接清零 limb 3/4 不折回（改为 `uint320_fold` 跨 limb 2/3/4 全部 ×5 折回），bug 1 与 bug 3 互相掩盖须同修；并配套修正密文长度，靠逐 lane `keep` 与 `axis128_keep_count` 让 Poly1305 长度字段认证真实字节数而非填充长度。验证上引入独立的纯 Python 参考模型 `aead_ref_model.py`，调业界 `cryptography` 包，在导入期跑 RFC 8439 §2.8.2 已知答案自检，贯彻「被测设计不能验证自身」原则。核心结论：C 版算出的 tag 是「自洽但不合规」的非标准 MAC，能跟自己通却无法与任何合规 WireGuard peer 互通；Pypeline 版因此故意与 C 版产生不同 tag 与长度，换取 RFC 8439 互通性。
