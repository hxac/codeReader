本讲以 B200 上 BF16 GEMM+ReLU 为实例，建立三级剖析流水线。Proton 按内核聚合次数/均值/累计时间来选靶：warmup 须在 proton.start 之前完成，排名看累计而非平均时长；它无时间戳，看不到内核顺序与间隙。Nsight Systems 给应用级时间线：区分 API 时间与 GPU 执行时间，用 trace 时间戳手算内核间隙、判断同步是否真在等 GPU；cudaProfilerStart/Stop 只圈采集范围、不计时。Nsight Compute 经内核重放读硬件计数器，按 LaunchStats→Occupancy→SpeedOfLight→SchedulerStats→WarpStateStats→SourceCounters 顺序读报告，产出 compute/memory/latency 瓶颈分类。核心结论是个反转：GEMM 的 Compute 吞吐 77.74% 并非 compute-bound——发射槽仅 3.2%、No Eligible 达 96.11%、Long Scoreboard 约占等待 87%，真瓶颈是 L1TEX 数据依赖叠加驻留 warp 不足，改进方向为提高驻留或缩短依赖链。口径纪律：三条吞吐各自以自身峰值为分母、不可相加；occupancy 是驻留并发度而非性能度量；NCU 的 Duration 只属被剖析运行，跨实现比较须回未剖析的 CUDA events 基线。
