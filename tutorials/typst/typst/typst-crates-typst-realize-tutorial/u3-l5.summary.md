本讲从调用方视角看 `realize` 如何贯穿 Typst 编译架构。它通过「函数指针表 `Routines`」分发而非被直接 use：实现由顶层 crate `typst` 经 `static ROUTINES` 一次性注册、再由 `Library.routines: &'static Routines` 挂载，调用方写 `(engine.library.routines.realize)(...)` 间接调用——这套「声明→注册→挂载→分发」四步链路用于切断 crate 间循环依赖（注释称之为支持 crate 拆分的动态链接）。全仓库共 8 个调用点，按 `RealizationKind` 归类为 Bundle×1 / Document×2 / Fragment×2 / Par×1 / Math×2：`typst-layout` 三处（pages=Document、flow=Fragment、inline=Par）共用「重建 Engine→新建 `Arenas`→调 realize→下游排版」同构模板；`typst-html` 复用 Document/Fragment/Math 三种 kind 但下游换成 `convert_to_nodes` 转 HTML 节点；`typst-bundle` 用空规则表的 `Bundle` 只做最小规整；`typst-library/math` 用 `Math` kind 且复用 `self.arenas` 而非新建。核心结论：`realize` 只负责把任意 content 规整成扁平、后端无关的 `Vec<Pair>`，至于清单拿去做 Frame、HTML 节点还是 bundle 资产，完全是各消费方自己的事——它是 eval 与 layout/导出之间的唯一桥梁。
