本讲把「`Eval` trait + `Vm` 虚拟机 + `ast::Expr` 总分发器」框架应用到 `typst-eval/src/math.rs`，阐明数学模式的求值机制，并指出它与 Markup 模式高度同构，只是叶子节点换成数学元素、标识符查找走专门作用域。核心结论包括：一是方程分两层，`Equation` 是 `$ ... $` 外壳（由 `$` 内侧是否带空格决定行内/块级），`Math` 是表达式流，逐个 `eval_display` 后用 `Content::sequence` 拼接。二是 `MathText` 区分 Grapheme（字形，打包成 `SymbolElem`）与 Number（数字，打包成 `TextElem`）。三是 `MathIdent` 走 `scopes.get_in_math`，其 fallback 查 `base.math` 而非 `base.global`，并产生专属的 `unknown_variable_math` 错误——这是数学标识符与代码模式的本质区别。四是 `ExprExt::eval_display` 作为统一显示接口，把异构的 `Value`/`Content` 产出转成带 span 的 `Content`，供序列拼接。五是 `MathFieldAccess` 直接复用 `code.rs` 的 `pub(crate)` 自由函数 `access_field`，以保证代码/数学两模式下字段访问（含 settable 字段的 context 兜底）语义一致。六是 `MathFrac::eval` 借助 `Math::was_deparenthesized` 计算出 `num_depar`/`denom_depar` 两个布尔标记，把「源码里是否写过括号」这一语法信息随 `FracElem` 带到排版期，供 Horizontal 风格分式决定是否重画括号，体现 typst-eval 作为「语法→运行时」桥梁的定位。此外，绕过 `Expr::eval` 总分发器的节点（如 `MathAccess::eval`）须手动调用 `vm.trace_at` 以满足 IDE 追踪约定。结构化节点（`MathDelimited`、`MathAttach`、`MathPrimes`、`MathRoot` 等）统一遵循「读子节点→构造强类型元素→`.pack()` 成 `Content`」的套路。
