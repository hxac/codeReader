本讲在 u5-l1 的「字节容器」之上，补全 wrapper function 的完整调用流水线。核心结论：跨进程调用收敛为统一的异步 C 签名 `orc_rt_WrapperFunction`，即 `void(Session, ArgBytes, Return, CallId)`——返回 `void` 意味着「完成」只能靠回调 `Return(S, ResultBytes, CallId)` 通知；`CallId` 是调用方提供、handler 原样回传的不透明令牌，用于配对调用与结果。引入的关键术语：统一异步签名、Return 返回回调、CallId 回环、方向不对称（controller→executor 按地址、executor→controller 按 tag，签名却相同）。执行端 `WrapperFunction::handle` 借助抽象的 `Serializer` 编排「反序列化参数 → 调 handler → 序列化结果 → Return」，并用 `yield` 回调把序列化从业务剥离；存在三处带外错误短路（上游错误透传、反序列化失败、序列化失败），与 u5-l1「先查带外错误再取数据」一脉相承。调用端 `WrapperFunction::call` 是 `handle` 的镜像，并把「传输」委托给 `Caller`（测试用 `DirectCaller`、生产用 `ControllerAccess`），从而把传输与序列化解耦，在边界用 `make_error<StringError>` 提升错误为内部 `Error`。`AsyncMethod`/`SyncMethod` 适配器把「按对象地址调成员方法」模板化，签名首个实参恒为 `SPSExecutorAddr`，业务代码因此几乎不写序列化样板。本讲把 `Serializer` 当抽象概念，具体实现 SPS 留给 u6。
