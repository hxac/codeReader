本讲讲解 orc-rt 的任务分发机制：`DispatchFn` 与两种 Runner。核心结论是 Session 是协调者而非执行者，自身不挑线程模型，而是把每个工作单元封装成 `Task`（`move_only_function<void()>`），交给构造时注入的 `DispatchFn` 决定「何时何地」运行——这是典型的执行策略注入。关键设计是 Token 随 Task 移动：Session 在调用 `Dispatch` 前先领取托管代码 Token，并把它 move 进 Task lambda，使异步派发与 Token 保护解耦，Task 无论在哪个线程运行都受其覆盖。本讲引入两类 Runner：`QueueingRunner` 只把 Task 入队、由调用者通过 `runFIFOUntilEmpty`/`runLIFOUntilEmpty` 抽干，适合无线程环境与确定性单元测试；`ThreadPoolRunner` 是固定大小线程池，worker 用条件变量等待、从队尾取（LIFO）、Task 在锁外运行，析构时抽干残留任务。生命周期铁律：Runner 必须比 Session 长寿，析构开始后禁止再派发。
