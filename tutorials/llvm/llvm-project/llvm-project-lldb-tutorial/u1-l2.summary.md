本讲为 LLDB 代码库建立一张目录心智地图，把 u1-l1 的抽象组件在文件系统里落地。顶层目录分三类：构建文档类（cmake/docs/scripts/utils）、源码类（include/source/bindings）、产物示例类（tools/test/unittests/examples）。核心是 `source/`，它按职责拆成十几个并列静态库模块——Utility/Host/Core/ValueObject/Interpreter/Commands/Symbol/Target/Breakpoint/Expression/DataFormatters/Plugins 等，依赖自底向上：底层模块几乎不依赖他人，`API` 模块最后构建并聚合为 `liblldb`，因为它要链接几乎所有其他模块。公私分层是关键约束：`include/lldb/` 与 `source/` 子目录高度镜像，但公共 `SB*` 类（`include/lldb/API/`）承诺 ABI 稳定，`lldb_private` 不保证；`include/lldb/` 下无 `Plugins/`，证明插件是纯内部实现。`lldb-forward.h` 集中前向声明以打破循环依赖。插件按类别组织在 `source/Plugins/<类别>/<具体插件>/`，共三十多类，由配置时生成的 `Plugins.def.in` 注册表集中声明，受 `LLDBLayeringCheck.cmake` 分层校验约束；运行时由 PluginManager 按类别与优先级挑选。`tools/` 每个目录是薄壳入口：`lldb`（driver）与 `lldb-dap` 链接 `liblldb`，而 `lldb-server` 刻意不链接 `liblldb`，直接用内部库与插件，体现前后端分离。LLDB 既是调试器也是可复用库，Python/Lua 通过 `bindings/` 的 SWIG 绑定复用同一套 SB API。
