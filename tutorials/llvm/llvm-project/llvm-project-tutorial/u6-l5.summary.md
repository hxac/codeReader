本讲是后端单元（u6）收官篇，回答「后端那成千上万条机器指令的描述、编码、汇编串、指令选择模式从何而来」。核心是 TableGen 这门声明式 DSL 的「描述—生成」两段式工作方式：先用 `.td` 文件声明式描述，再由 `llvm-tblgen` 在构建期把描述编译成大量 `.inc` C++ 片段。

两个最小模块：其一为 `.td` 描述——`.td` 经 TGLexer、TGParser 解析后变成扁平的 `RecordKeeper` 记录数据库；引入的关键概念有记录（Record/def）、类（class，模板）、multiclass/defm（批量实例化）、let（字段覆盖）与 dag（`(op a:$name)` 形式的一等类型，统一表达操作数列表与 SelectionDAG 匹配模式）。一条指令即一个 Record，字段含 outs/ins、AsmString、Pattern、`bits<N> Inst` 编码、语义位等。以 RISC-V 的 `def ADDI : ALU_ri<0b000,"addi">` 为例，寥寥几行即描述完整指令。其二为后端代码生成——每个 `-gen-xxx` 生成器（如 `-gen-instr-info`、`-gen-dag-isel`、`-gen-asm-writer`、`-gen-emitter`）在各自 `*Emitter.cpp` 末尾用静态对象自注册，通过 `getAllDerivedDefinitions` 查询记录、遍历后吐出带「do not edit」头的 `.inc`；CMake 用 `set(LLVM_TARGET_DEFINITIONS)` 与一串 `tablegen(...)` 接入；目标代码以「宏开关 + #include」消费。本讲回扣前讲：u6-l2 的 `MatcherTable`/`OPC_MorphNodeTo` 正是 `-gen-dag-isel` 从 `.td` 的 Pattern 编译而来，u6-l1 目标类持有的 InstrInfo/RegisterInfo 即 `.inc` 产物。核心结论：TableGen 把新增后端的工作量从 N×K 降为 N+K，这是 LLVM 支持数十种架构的根基。
