本讲专讲 AR 模块的调度器层。vLLM-Omni 按 `StageExecutionType`（`execution_type`）分派调度器：`LLM_AR` 选 `OmniARScheduler`（同步）或 `OmniARAsyncScheduler`（异步），`LLM_GENERATION` 恒选 `OmniGenerationScheduler`，`DIFFUSION` 返回 `None`（走独立 diffusion 引擎）。该分派由纯函数 `_resolve_scheduler` 完成，同一个 `execution_type` 还串起 worker_type 与 model runner。两种调度器都嵌在统一请求流 `InputProcessor → Scheduler → Worker → ModelRunner → OutputProcessor` 中，差别只在 token 分配与结束判定。

`OmniARScheduler` 走「最小改动」：`schedule()` 完全委托 `super().schedule()` 做增量 chunked 分配，仅在尾部把原生 `NewRequestData` 重包装成 `OmniNewRequestData`，用 `getattr` 从活 `Request` 捡回 `prompt_embeds`、`additional_information`、`model_intermediate_buffer` 三类载荷，并在 `update_from_output()` 叠加 KV 迁移管理，靠 EOS/max_tokens 等多步停止条件结束。`OmniGenerationScheduler` 走「单步快路径」：`schedule()` 用 `max(len(prompt),1)` 一次性全量分配，`update_from_output()` 在输入全部算完时一步判完 `FINISHED_STOPPED`，专供 Code2wav 这类单步前向的基础异构结构。两者共享 `OmniSchedulerMixin` 的工具方法，下游「等上游载荷」由 `OmniSchedulingCoordinator` 的 `WAITING_FOR_INPUT` 状态统一管理。
