本讲承接 u3-l1 对 `config.yaml` 顶层结构的拆解，聚焦 `config/recipes/` 下"打包好、可直接交付"的路由配方（recipe），围绕三个最小模块展开。一是**配方目录**：仓库维护 7 个配方（accuracy、agent、balance、privacy、knowledge、feedback、multi-objective），目录刻意按"用户结果场景"而非实现细节（如 SAARS、Router Flow）命名，使用者可按业务目标挑配方，其中 `balance` 是推荐默认画像。二是**四文件交付契约**：每个配方目录必须恰好包含 `config.yaml`（v0.3 运行时权威）、`recipe.dsl`（可评审且可与 config 双向转换）、`probes.yaml`（正确性探针，借 `routing_assets` 与同目录资产绑死，并声明 `acceptance` 通过率）和 `README.md`，缺一多一都不行，且 config 不得含遗留顶层键。该契约由 Go 测试 `TestMaintainedRecipeDirectoriesAreCompleteAndSymmetric` 以目录/文件集合精确匹配白名单的方式强制，但只管"形态"。三是**配方校验**：语义正确性由 `vllm-sr validate`（解析后跑语义校验器，通过则打印含 entrypoints/recipes/decisions 计数的配置摘要）和 `go run ./cmd/dsl validate/compile`（DSL 合法性与往返一致）分担，二者互补。本讲还引入关键概念 **multi-objective 多入口配方**：单一 config 经 `entrypoints` 与 `recipes[]` 同时暴露 5 个互相隔离的目标，recipe 私有的信号/投影/决策不可跨 recipe 匹配，与 `balance` 这类单画像配方形成对照。
