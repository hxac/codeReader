本讲承接调度器核心，聚焦 V1 提升吞吐的两个机制及其承载队列。**连续批处理**让请求随时进出 batch 而不必等齐，在 V1 中并非独立模块，而是「统一 token 预算」的自然结果：每步 `schedule()` 先保 RUNNING、再接 WAITING，二者共用同一 `token_budget`，请求随到随算、随完随走，消灭静态批处理的「尾部气泡」。**分块预填充**用 `min(num_new_tokens, token_budget)` 把超长 prompt 切成多步，由 `enable_chunked_prefill`（默认开启）控制；未算完的请求留 `running` 并置 `is_prefill_chunk=True`，每步在 `_update_after_schedule` 中据 `num_computed_tokens < num_tokens` 刷新。**请求队列**由 `request_queue.py` 抽象，调度器维护 `waiting`/`skipped_waiting`/`running` 三态：新请求入 waiting，因依赖未就绪被跳过的进 skipped_waiting 优先重试，被抢占的 prepend 回 waiting 队首。两种策略 FCFS（deque）与 PRIORITY（堆）由 `SchedulerConfig.policy` 选择。三者合力使 prefill（算力密集）与 decode（带宽密集）同步混排，构成 vLLM 高吞吐的根基。
