本讲是「工程实践、对比基线生态与二次开发」单元的开篇,把项目里十余个对比基线当作生态俯瞰,不再深入单个内核。核心结论:基线可分四类——厂商库(cuBLAS/rocBLAS/CK/aiter,代表硬件天花板)、DSL 或编译器(Triton/BitBLAS/Welder-Ladder/TileLang 主角,靠 autotune 搜调度)、专项内核(Marlin 做 W4A16、CUTLASS fpa_intb、FA3、bitsandbytes nf4)、参考实现(torch eager,用于数值校验与朴素下限)。关键概念:「provider」即同一算子在同一架构下并列对比的实现;主角 TileLang 通常置于编号 `1./2./3.` 子目录,基线在 `0.`。引入两个要点:一是「基线名≠库名」,目录俗称与实际 import 不符——`ladder` 实为 `welder`、`deepgemm` 实为 BitBLAS fp8、`rocblas` 目录为空占位,读源码以 import 为准;二是依赖安装三范式,pip 直装(bitsandbytes) < 源码可编辑安装(Marlin/aiter) < 编译整个宿主框架(CUTLASS fpa_intb 编译 TVM 并钉死 commit)。架构归属:aiter/CK/Ladder/rocBLAS 为 AMD 专用,cuBLAS/CUTLASS/bitsandbytes/DeepGEMM 为 NVIDIA 专用,Triton/BitBLAS/torch/Marlin 跨架构。各基线计时口径不一(cuBLAS 用 µs、Triton/BitBLAS 用 ms、CK 走 C++ 二进制),跨框架对比须先统一单位,为 u7-l24 跨架构适配与 u7-l25 新增算子基准奠基。
