本讲聚焦一个问题：当形状与 dtype 在调用时才推断（input-inferred）时，TileOPs 如何决定一次调用是否重新 JIT 编译 kernel。涉及三个核心机制。其一，`_static_axes` 是挂在 Op 类上的 `frozenset[(input_index, axis)]`，记录「构造期已提交」的轴；reduction 家族因 reduction 轴依赖 `dim` 参数，需在 forward 里归一化 `dim` 后动态绑定，它是 manifest `static_dims`（R20）的代码侧投影。其二，`_cache_key(*input_shapes)` 是 Op 层的「投影契约」，默认实现排除已提交轴，把原始形状坍缩到 kernel 真正特化的维度，避免 over-fragmentation（过度碎片化）；空 `_static_axes` 且未覆写时触发一次性 `UserWarning`，`GemmOp`/`BmmFwdOp` 将其投影到 `(m,n,k[,batch],trans,dtype)`。本讲强调它当前为声明式契约，与运行时缓存 key 概念对齐却各自独立。其三，kernel 复用分两层：`_kernel_cache` 字典跨不同形状懒构建复用，`_active_sig`/`_active` 则在连续相同签名时跳过校验、形状推断与查表。由此引出 lazy build（input-inferred 算子）与 eager build（构造期形状即定的算子）的对比，以及 fixed-rank 与 arbitrary-rank 在维度推断时序上的差异。
