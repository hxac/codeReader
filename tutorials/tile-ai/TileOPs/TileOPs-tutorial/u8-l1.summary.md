本讲解答 Op 三个 codegen 契约方法（`_validate_dtypes`、`_infer_output_shapes`、`eval_roofline`）的方法体从何而来：它们不由人手写，而由 `Op.__init_subclass__` 钩子在子类**定义**（非实例化、import 即触发）瞬间据 manifest 元数据自动合成安装。三个最小模块：① 钩子里两行 `maybe_install_*` 用懒导入打破 `op_base` 与两个 codegen 模块之间的循环依赖；② 两个安装函数共享四级判定流水线（override 检测 → manifest 解析，先看类属性 `__manifest_*__` 再按 `cls.__name__` 查 YAML → `status == "implemented"` 关卡 → 合成并 `cls.XXX = fn`），其**关键不对称**为 dtype 侧只看 `cls.__dict__`（家族基类手写版会被遮蔽）、roofline 侧遍历整条 MRO（家族基类版被保留、静默继承），故 `test_pool_codegen_slots_are_class_local` 强制两 slot 必须落在具体类 `__dict__`；③ `status: spec-only` 是 codegen 总开关，非 `implemented` 一律跳过、保留基类抛 `NotImplementedError` 的 stub（当前是普通方法而非 `@abstractmethod`，附 `FIXME(staged-rollout)`）。核心取向：codegen 是「尽力装」（合成失败被吞、不阻断 import）、manifest 验证器才是权威关卡；翻转 `status` 即自动获得真实体、无需人改代码，对应信任模型「逐 op、逐 PR 迁移」。
