本讲承接 `lower_tl` 链路，回答「注意力 kernel 用多大的 tile、多少线程、几级流水才能跑得快，且能否自动确定」这一问题，拆为五个最小模块。硬件建模上，`Arch`（`arch_base.py` + `H100`/`A100`/`RTX4090`）是一张静态硬件规格表，含 `smem_cap`、`reg_cap`、`register_per_thread`、`mma_primitive`、`threads_per_mma`，按 compute capability 分派，未登记则回退 H100。`memory_usage` 用解析式估算一份配置的 shared memory（Q/K/V/scores/acc_o 五项，K/V 乘 `stages`，累加器按 fp32 的 4 字节）与每线程寄存器占用，无需运行。`decider` 以 mma 原语为步长笛卡尔枚举 `block_M`/`block_N`/`block_K`/`num_threads`/`stages` 等，经三道硬件上限加 warp 对齐与 `block_K==dim_qk` 过滤，但目前尚未接线（调用被注释），真正在跑的是运行期调优。运行期路径为 `tune`/`tune_file` → `TunnerOutput` → 模板 `{{TUNE}}`/`{{TUNE_FILE}}` → TileLang `@autotune` + `tune()` 助手 + 按 `{B,H,N_CTX,D_HEAD,D_HEADV,causal}` 键的 JSON 缓存，Arch 模型当前仅在反向 `get_bwd_configs()` 接入。另有独立的离线搜索器 `AttnFwdTunner`（编译并行、计时串行），与模板内 `@autotune` 共用缓存键、可互换复用 JSON。核心结论：静态过滤与硬件建模已就绪但待接线、前向搜索空间与 Arch 的接入尚不完整，是明确的改进方向。
