本讲拆解 `T.Pipelined` 背后的软件流水线编译链，说明它如何让访存密集 kernel 的「搬运」与「计算」时间重叠以隐藏延迟。核心是两个配合的 pass：`tl.PipelinePlanning` 负责规划——分析每条语句的读写，把消费者分到 `stage=num_stages`、把喂数据的 copy 分到 `stage=0` 并排到消费者之后，再标注异步生产者；`tl.InjectSoftwarePipeline` 负责改写——把单循环拆成 prologue/steady/epilogue 三段，对 shared buffer 做多版本化（用 `floormod` 选版本，标准 GEMM 下版本数恰为 `num_stages`），并插入同步。`num_stages` 即 copy 与 compute 之间保留的缓冲份数（2 即经典双缓冲），0 表示不流水。引入的关键术语包括生产者/消费者、stage/order、`cp.async` 及其 `commit_group`/`wait_group`、Hopper 的 TMA 与 mbarrier 的 expect_tx/wait_parity 奇偶握手模型（屏障被复制成 `num_stages` 份分槽）。重要结论：metax 分支在规划阶段对 MACA 强制关闭异步拷贝，因此 MACA 上的流水线仍做多版本化与三段拆分，但 copy 为同步，重叠收益弱于 CUDA。
