本讲精读 `workers.rs` 的 `tun_worker`：出站方向（本机→对端）数据的第一个处理者，每个 TUN reader 一条、阻塞常驻，职责是「读明文 IP 包→填充对齐→交给路由器」，自身不做密码学。

每轮循环顶部原子重载 `wg.mtu`；按 `mtu + SIZE_MESSAGE_PREFIX(16) + 1 + CAPACITY_MESSAGE_POSTFIX(16)` 分配 `msg` 缓冲区——前缀 16 字节留给就地（in-place）写入的传输头，后缀 16 字节留给 AEAD 认证标签，`+1` 是安全 slack。`reader.read(msg, 16)` 按 Tun::Reader 的 offset 契约把 IP 包写入 `buf[16..]`。

核心函数 `padding(s,m)=min(m, ⌈s/16⌉×16)`：载荷按 `MESSAGE_PADDING_MULTIPLE`(16) 向上对齐且不超 MTU，返回值要么等于 MTU、要么是 16 的倍数。之后 `wg.router.send` 经 `Device::send`（跳过前缀、按目的 IP 在 cryptokey 路由表 `get_route` 选 peer）调 `Peer::send(msg, true)`。

关键结论：无密钥时包进 `staged_packets` 暂存并触发 `need_key` 回调发起握手，握手后由 `send_staged` 补发，用户数据不丢；`mtu==0`（down 态）用 `continue` 丢包但保留线程，`read` 出错才 `break` 永久退出，配合 `WaitCounter` 生命周期。后续讲义将沿 `SendJob` 加密、`udp_worker` 入站对照、有序队列 Queue 继续展开。
