本讲承接 u2-l3 的 `bpe->encode`，回答「BpeTokenizer 对象如何从 model.json 构造」。引入两个被 BPE/Unigram 共用的纯数据结构：`SpecialTokensConfig`（7 个 `optional<string>`，描述配置字符串）与 `SpecialTokenIds`（7 个 `int` 默认 -1，描述解析后 id），二者分离「人类可读配置」与「模型所需整数」。核心结论有三：其一，gpt 主运行时里 `tokenizer.type` 只在 bpe 与 bbpe 间切换（同为 BpeTokenizer，靠 `use_byte_encoder` 开关控制 InitByteMaps），真正的 unigram 分支只在嵌入运行时；其二，eos/bos 经 `token_to_id().at()` 解析为 id，空串保护得 -1，拼错字符串则抛异常被构造函数 catch 转成 load model failed，是刻意尽早失败；其三，额外特殊令牌如 `<|image_pad|>` 须单独注册，encode 时以最长子串匹配整体识别为原子 id、绕过 BPE 切分，是 VLM 后续 inject_image_embeds 整段替换占位的前提。必需令牌用 `.at()` 报错、可选令牌用 `.find()` 静默得 -1，体现「必需 vs 可选」的区分设计。
