本讲义从「报告本身」而非报告内容切入，讲清 Vivado 报告的生成机制与文件格式。核心结论：每份报告都由一条 Tcl 命令产生——时序报告用 `report_timing_summary`，利用率报告用 `report_utilization`；命令被原样回显在报告头部的 `Command` 字段中。参数 `-file` 必产出纯文本 `.txt`，`-rpx` 仅在命令显式写出时才额外产出 Vivado 交互格式 `.rpx`。因时序命令一律带 `-rpx`、利用率命令从不带，故本仓库时序报告 `.txt` 与 `.rpx` 成对出现，利用率报告只有 `.txt`。

报告头部元信息是报告的「身份证」，包括 Tool Version、Date、Host、Command、Design、Device、Speed File，仅利用率报告额外有 Design State 字段。由头部可判定工具链、设计归属、批次同源与可复现性。引入的关键陷阱：同一器件在三类报告中写法不一致（`7a100t-csg324`、`xc7a100tcsg324-1`、`.rpx` 内键值对形式第三种），脚本匹配器件名需兼容多种写法。

格式对比上，`.txt` 为纯文本，可 grep、可 diff、可脚本解析，是版本管理与批量提取指标的唯—可靠数据源；`.rpx` 为二进制序列化的报告数据模型，专供 GUI 折叠、排序、钻取，不可当文本解析，与同名 `.txt` 数据等价，丢失 `.rpx` 不丢数据。本讲为后续方案对比（依据 `Design` 名区分 `cic_compiler_0`、`CIC_R…_N…`、`cic_d` 三种实现）与实验矩阵梳理奠定同源判定基础。
