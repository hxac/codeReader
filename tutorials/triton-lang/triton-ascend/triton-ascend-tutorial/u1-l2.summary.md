本讲建立 Triton-Ascend 仓库的「导航图」，核心是「Triton core 与 Triton-Ascend」的分层原则。仓库只有两条代码线：core 存放目标无关（target independent）的通用实现，家园是 `python/`（Python：`@triton.jit`、JIT、缓存、TTIR 生成）与顶层 `include/`、`lib/`（C++/MLIR 通用方言与 GPU 转换）；ascend 存放目标亲和（target affinitive）的昇腾专属代码，家园是 `third_party/ascend/`，内部分 `language`（cann 语言扩展）、`backend`（compiler.py+driver.py+backend_register.py 按 torch_npu/mindspore 分派）、`include/lib`（约 14 个 lowering pass，如 TritonToLinalg）、costmodel 等。判定标准是「删掉它会坏所有后端还是只坏 Ascend」。分层由安装期机制强制：`setup.py` 用拷贝或开发模式符号链接，把 ascend 的 `language` 挂载成 `triton.language.extra.cann`、把 `backend` 放进 `triton.backends`，再由 core 的自动发现（entry points）加载。分层并非绝对纯净：core 保留了少量中性扩展点钩子（如带保护的 `_try_import_ascend`、`ascend_builder` 插槽），ascend 也用运行时 monkey patch 改 core 行为，但改动代码体始终留在 ascend 子树。易错点：`third_party/ascend/include` 与顶层 `include` 同名却完全不同。
