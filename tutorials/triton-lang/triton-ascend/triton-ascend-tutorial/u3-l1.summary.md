本讲是 Triton 编译流水线的入口，只覆盖 Python 到 TTIR 这段，含三个最小模块。`@triton.jit` 是装饰器：把普通函数替换成待编译的 `JITFunction`（解释器模式下为 `InterpretedFunction`），构造时不编译，仅缓存签名、按设备懒加载 binder。`kernel[grid](args)` 经 `KernelInterface.__getitem__` 返回记 grid 的 lambda，调到 `JITFunction.run`；run 按「特化＋设备」查缓存，未命中才在 `_do_compile` 调 `self.compile` 触发编译，而它经 `create_binder` 绑定为 core 的 `triton.compiler.compile`。`compile()` 是总调度：`make_backend` 靠 `supports_target` 判定 `backend=="npu"`，选中唯一的 `AscendBackend`（继承 `BaseBackend` 契约），用 `add_stages` 注册阶段流水线。核心结论：TTIR 分两步生成——原始 TTIR 由 core 的 `ast_to_ttir` 遍历 Python AST 产出、目标无关；优化由后端首阶段 `make_ttir` 跑通用 pass（inliner/cse/licm 等）完成。此外，仓库里的 `jit.py` 是干净上游原貌，Ascend 对它的整型注解特化定制以补丁形式在构建期由 `setup.py` 贴上，印证去侵入化机制。
