本讲覆盖 Triton 编译流水线的「入口」（Python 到 TTIR），含三个模块。`@triton.jit` 是装饰器而非立即编译，把函数替换成待编译的 `JITFunction`（解释器模式为 `InterpretedFunction`），构造时不编译。`kernel[grid](...)` 经 `KernelInterface.__getitem__` 记下 grid 调到 `JITFunction.run`，按「特化 + 设备」查缓存，未命中才编译，触发点是 `self.compile`，经 `create_binder` 绑定为 core 的 `triton.compiler.compile`。该函数作总调度：`make_backend` 据 `GPUTarget` 选出唯一的 `AscendBackend`（`supports_target` 判 `backend=="npu"`），再由后端 `add_stages` 注册阶段流水线。核心结论：TTIR 分两步生成——core 的 `ast_to_ttir`（遍历 Python AST）产出目标无关的原始 TTIR，后端首阶段 `make_ttir` 跑通用 pass 做优化。`BaseBackend` 抽象基类定义后端契约，Ascend 借此插入编译流程。
