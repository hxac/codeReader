本讲从全景拉近到仓库「骨架」，讲解 Vitis_Libraries 单仓库（monorepo）的目录约定与跨库配置：顶层并列 9 个加速库目录（utils、data_mover、dsp、solver、blas、vision、security、motor_control、ultrasound），各库内部统一遵循 L1/L2/L3 三层目录约定（L1 原语头件、L2 内核与示例、L3 应用流水线）。

核心结论有四：其一，每个库用 library.json 声明身份与编译需求——v++.includepaths 与 host.compiler.includepaths 分别为内核侧、主机侧提供 include 路径（LIB_DIR 为占位符，工具链替换为库根目录，两侧路径分开声明），部分库（如 vision）还用 host.linker.libraries 声明链接库。其二，dependency.json 用 dependsOn 表达库间直接依赖，可递归算出传递依赖闭包；主干链为 solver→dsp→data_mover→utils，utils 是多数库的公共根，而 blas/vision/motor_control/ultrasound 为无依赖孤岛，使用某库时须将其闭包一并引入。其三，platform_map.json 把逻辑平台名（如 vck190）映射到具体 .xpfm 文件名，目前仅列 4 个 Versal/AIE 平台，使脚本与平台版本解耦。其四，顶层 Jenkinsfile 仅两行，借助共享流水线库 pipeline-library 的 FullVitisLibPipeline 统一驱动全部库 CI，形成「薄入口+厚共享库」两层结构。
