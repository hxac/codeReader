本讲围绕 `modeling/transformers` 这个 uv 子项目，讲解如何回答「monkey-patch 后到底快了多少、GPU 计算有多少真正落在 TileGym 内核上」两个工程问题，核心是 `tilegym-hf-bench` CLI 及其三个等价入口（控制台脚本、`-m` 模块调用、`infer.py` 兼容垫片，最终都汇入 `_cli.py:main`）。

关键术语：`--use_tilegym`/`--use_cutile`/`--use_attn` 三个布尔开关决定是否打补丁、是否切 cuTile 后端、是否替换注意力，且 patch 必须早于模型实例化；后端判定由 `_detect_backend` 给出（`use_tilegym` 且 `use_cutile` 才返回 cutile）。两条 profiling 路径：`--profile` 走应用内 `torch.profiler`，产出 CSV 与 Chrome trace；`--report_kernel_coverage` 走 nsys，采用「外层剥标志 + nsys 包子进程」的双进程自递归架构，读 `.nsys-rep`→SQLite→查 `CUPTI_ACTIVITY_KIND_KERNEL` 的 demangledName。

核心结论：`KernelFilter` 是两条路径共用的「判官」，规则为 YAML 里的 `prefixes`（子串包含，非真前缀）配 `blacklist`（整串相等），`aten::matmul` 黑名单是子串误伤的典型修补。kernel coverage 定义为命中内核的 GPU 时间占比与 launch 次数占比两个比值；它既是工程指标也是配置约定——改 YAML 一行，分子即变。该工具可诊断「主干已替换、零碎 op 未融合」的画像，为下一步融合优化提供依据。
