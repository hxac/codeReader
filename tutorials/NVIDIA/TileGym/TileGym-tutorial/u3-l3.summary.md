本讲专讲 cuTile 内核的「主机侧启动逻辑」，即内核编译好后如何由 Python 侧提交到 GPU。主样本为 softmax.py 的四个 `_launch_*` 函数与 `_Softmax` autograd 封装。核心结论：grid 计算分两种调度——静态持久化用 `num_programs = min(NUM_SM × occupancy, n_rows)`（即 grid-stride 循环，每块跨步处理多行），其中 `occupancy` 必须与内核装饰器 `@ct.kernel(occupancy=K)` 的 K 一致（提示给编译器、派发给运行时同数），多波调度则 `grid = n_rows`、一块一行、不依赖 NUM_SM 也无需 occupancy 提示。每个启动函数在算完 grid 后、启动前都必须对张量入参调 `.contiguous()`，因内核按紧密行主序算偏移，非连续视图会读错数据；已连续时零开销，仓库有就地手写与 `_ensure_contiguous` 装饰器两种写法。`ct.launch` 是仅位置参数的四参调用 `(stream, grid, kernel, kernel_args)`，`kernel_args` 为元组、按内核形参位置排列、名字不必一致、`ConstInt` 形参传入 Python int 即被特化。`_Softmax.forward` 按 `use_multi_wave → use_chunked → use_tma → basic` 四路分发（TMA 与 chunked 互斥，低架构 compute capability<9 时 TMA 自动回退 basic），输出张量 `torch.empty_like` 由主机分配，`TILE_SIZE = next_power_of_2(n_cols)`，chunked 再与 `MAX_TILE_SIZE=8192` 取 min 以强制分块。引入的关键术语：主机侧/设备侧、SM（multi_processor_count）、occupancy、grid-stride 循环、多波调度、`.contiguous()`、`ct.launch` 四参、策略分发。算法本身的差异留待 u3-l4 展开。
