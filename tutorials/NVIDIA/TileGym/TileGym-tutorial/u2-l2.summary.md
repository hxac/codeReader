本讲剖析 TileGym 后端分发器 dispatcher.py 的运行时机制，覆盖四个模块。`_REGISTRY` 是模块级可变全局嵌套字典 `{算子:{后端:实现}}`，初始为空、随导入生长，`@dispatch` 另把 stub 登记为仅供自省的 `"default"` 键（由 `get_available_backends_for_op` / `get_registry_info` 等函数消费）。`register_impl` 原样返回 func，注册作为「导入副作用」发生，受 `ops/__init__.py` 的条件导入门控，故注册表随运行环境而变。`dispatch` 是装饰器工厂，返回的 `wrapper` 借闭包记住 name / fallback_backend / default_impl，并用 `@functools.wraps` 保留 stub 签名，查找分五个决策点（取显式 backend → 定当前后端 → tilecpp 健康检查 → 查当前后端 → 查兜底/默认）。fallback 三处工程细节：tilecpp 延迟且缓存的可用性探测、`_LOGGED_WARNINGS` 三元组去重、`DISABLE_FALLBACK` 作用在两个位置且每次调用现读环境变量。核心结论：一次 `ops.softmax(x)` 经 `wrapper → _REGISTRY 查表 → _Softmax.apply → _launch_softmax_kernel → ct.launch` 完成，最短路径仅五步，是理解「接口—分发—实现」三层架构的最佳样本。
