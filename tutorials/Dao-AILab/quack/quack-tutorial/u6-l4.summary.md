本讲介绍 `@gemm_epilogue` 函数式创作前端：把一个对累加器逐元素求值的普通 Python 函数，降低（lower）到已有的 `EpiOp` 机制上，免去手写 mixin。核心心智模型是「函数即组合点、EpiOp 即扩展点」——计算顺序由源码显式写明，新 op 只需声明端口即可组合。函数契约为 `fn(acc, **operands) -> {"D":..., <sinks>...}`，`acc` 必须首参，省略 `"D"` 表示保留原始累加器。

讲义引入的关键术语：`fn_port` 值端口协议（`row`/`col`/`tile`/`scalar`/`value`/`apply`/`sink` 七种，前端只按该属性分发、绝不 `isinstance` 分发），及 `fn_prepare`/`fn_apply`/`fn_sink_flush` 三个端口方法；铸模（mint）机制 `_mint`，按 `(种类签名, SM, 模式)` 动态 `type(...)` 出继承 `_EpiModMixinBase` 的标准 mixin 子类，缓存于 `_minted`；语义指纹（fail-closed，深度指纹函数源码加各 op `cache_key()`）；跨进程身份 `GemmClassRef`，使 JIT 缓存收可 pickle 配方而非类对象，同摘要即同 `.o`。

核心结论：函数式与手写 mixin 共享同一套 EpiOp 机制而非两套框架；逃生出口分级存在（`ops=` 钉单参 → 加端口方法 → `epilogue_from_class` 退回 mixin）。`apply` 端口协议已就绪但本 HEAD 暂无内置 op 使用。
