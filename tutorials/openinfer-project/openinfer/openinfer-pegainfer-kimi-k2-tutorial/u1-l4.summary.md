本讲覆盖 Kimi-K2 的构建体系与引擎入口，涉及的最小模块为 Cargo.toml 的 feature 定义、lib.rs 的 launch、model_line.rs 的 ModelLine 实现与 runner/bringup.rs 的 start_engine。核心结论：默认构建是空壳，`kimi-k2` feature 点亮本 crate 运行时模块并把 CUDA 编译传导给 pegainfer-kernels（`kernel-report` 是叠加 trace 的观测超集），构建必须 `--release`；服务器二进制纯分发，模型经 `ModelLine` 三步接入——`probe` 按 config.json 的 model_type 过身份门，`augment_cli` 注入 `--ep-backend`（取值 nccl/deepep，默认 deepep）并消费 tp_size/dp_size/cuda_graph，`launch` 组装 KimiLaunchOptions，dp 缺省补 8 故默认拓扑 TP1/DP8。lib.rs 的 launch 是 EP 拓扑策略唯一 owner，产出 EngineLoadOptions（设备表 0..ep_world、seed 42）交给 bringup::start_engine，后者打 resolving 日志、验设备数并按 (TP,DP) 分派两路：TP8/DP1 须 nccl，TP1/DP8 须 deepep；库路径不传 parallel_config 时回退 TP8/DP1，与 CLI 默认刻意不同。后续讲义沿用术语：feature 传导、ModelLine、TP/DP/EP、ParallelConfig、EngineLoadOptions。
