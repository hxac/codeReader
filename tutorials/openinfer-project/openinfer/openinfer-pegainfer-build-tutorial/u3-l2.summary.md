本讲从消费方视角对比两个 build.rs 如何使用 CudaToolkit 的四个出口（root、nvcc、include_dirs、lib_dirs）。kernels 是最重消费方：全文件仅一次 discover()，派生 nvcc 命令与 cuda_include（header_dir 按具体头文件单点定位，None 时兜底 root/include），该目录以 -isystem 喂 nvcc、以 -I 喂宿主 cc，借优先级差让 vendored CCCL 覆盖 CTK 旧版；root 另拼 kernel-lab 与 Windows 库目录。cupti 是最小消费方：不用 nvcc，直接遍历 include_dirs，用公开 root 拼 extras/CUPTI 组件特例目录，并以 is_dir() 软门控优雅降级。核心结论：出口一半变编译器 argv、一半变 cargo: 指令，lib_dirs 私有、仅经 link_search() 输出；None 兜底在 conda 布局下指向存在却缺 CUDA 头的目录，把探测失败变成含糊编译错误，宜以断言加提示快速失败；「库管通用布局、消费方管组件特例」是 API 边界分工原则。关键术语：宿主 cc 与 nvcc 的找头差异、-I 与 -isystem 的优先级差、cc crate、软门控。
