本讲剖析 save 链路。`build_saves` 把一组（block_id, hash）扇出为每层一份的 LayerSave：块号与哈希跨层不变，i32→usize 块号转换只在此边界做一次。`submit_save` 是异步本体（spawn + oneshot + keep_alive）：keep_alive（典型为源块的 allocator guard）被移入后台任务，直到异步 D2H 拷贝落地之后才 drop。因 pegaflow 的 D2H 拷贝流与计算流无依赖，调用方必须维护两条契约：排序契约（ORDERING）要求只保存 forward 步同步后的已封块，否则读到撕裂数据；重用契约（REUSE）要求源块在拷贝落地前不可被回收重用，否则错请求的 KV 会以旧哈希静默持久化进 host 池。对外仅两种形态：save 是 fire-and-forget，错误唯一出口是 oneshot send 落空后的日志兜底；save_blocking 同步等待、错误上抛、返回即可重用源块；SaveHandle 为 crate 私有。生产接线在 qwen3 的 save_sealed_blocks：步同步后调用并以 guard 精确 pin 满足两契约。核心结论：丢一次 save 只损命中机会，契约失守才是致命的错字节进池。
