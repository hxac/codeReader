本讲讲清 veRL 单控制器中「方法如何被分发执行」的机制，核心是 `@register` 装饰器与 `Dispatch` 枚举。`@register` 不改变方法功能，只把 `dispatch_mode`/`execute_mode`/`blocking` 存入一个魔数属性 `MAGIC_ATTR` 打在函数对象上；`WorkerGroup._bind_worker_method` 创建时扫描这些标签，用 `func_generator` 把方法重绑成「分发—执行—收集」三段式壳子，实现业务逻辑与数据搬运的解耦。`Dispatch` 枚举是「配送方式目录」，经 `get_predefined_dispatch_fn` 查表翻译成一对 `dispatch_fn`/`collect_fn`；`Execute` 枚举只决定全员执行（ALL）还是仅 rank 0 执行（RANK_ZERO），也可用自定义 dict 绕过预定义表。两类最常用模式：`ONE_TO_ALL` 广播，复制参数 `world_size` 份、输出原样返回列表，用于 `init_model`/`save_checkpoint` 等无数据、全员同构场景；`DP_COMPUTE_PROTO` 数据并行，对 `DataProto` 做 `chunk(world_size)` 切分、`concat` 拼回，底层为 `_split_args_kwargs_data_proto` 与兼容同步/异步的 `_concat_data_proto_or_future`。判据：方法参数含 `data: DataProto` 要并行处理则用 `DP_COMPUTE_PROTO`，否则用 `ONE_TO_ALL`。本讲作为 u3-l1 的 `chunk`/`concat` 与 u3-l2 的 `func_generator` 之间的粘合层，为后续 u4 PPO 主流程阅读奠定基础。
