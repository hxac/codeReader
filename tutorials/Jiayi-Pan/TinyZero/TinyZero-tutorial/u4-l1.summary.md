本讲精读训练总装入口 `verl/trainer/main_ppo.py`，它是「配置→训练」之间的总装车间，本身不含任何训练算法，只做组件拼装。核心模块有二：装配流水线 `main_task` 与奖励路由。`main_task` 是被 `@ray.remote` 装饰的远程函数，由 Hydra 入口 `main` 用 `ray.get(main_task.remote(config))` 提交并阻塞等待；它依次按 `strategy`（fsdp/megatron）选 Worker 后端与 WorkerGroup 类、组装三张表、实例化奖励函数，最后交给 `RayPPOTrainer` 的 `init_workers()` 与 `fit()` 点火。关键结论是三张表构成「角色→物理资源」的两跳链路：`role_worker_mapping`（角色→Worker 类）、`resource_pool_spec`（池名→每节点 GPU 数列表）、`mapping`（角色→池名）；TinyZero 默认 ActorRollout/Critic/RefPolicy 全部 colocate 到同一 `global_pool`，且 actor 与 critic 必须同后端。奖励侧，`RewardManager` 是可调用对象，有双重身份：batch 含 `rm_scores` 时直接返回（model-based 短路），否则逐条解码、按 `data_source` 路由规则函数打分（rule-based，TinyZero 走这条）。`_select_rm_score_fn` 是接入新任务的核心扩展点，用子串匹配路由，未登记的 `data_source` 会抛 `NotImplementedError`；新增任务需改三处代码（新建奖励文件、加 import、加路由分支）外加数据侧约定 `data_source`。标量奖励最终挂在每条回答最后一个有效 response token 位（`reward_tensor[i, valid_response_length-1]`），形成稀疏奖励供后续优势反传。本讲只到点火，`init_workers` 与 `fit` 内部留给后续讲义。
