本讲是架构收尾篇，不引入新模块，而是把前述零件拼成一台完整机器，回答数据流如何走、为何这样切分、性能靠什么撑住三个问题。最小模块为决策心脏 `shouldShowSource`、更新中枢 `checkUpdateAction`（把更新归纳为 rebuild/skip/none 三动作）、总开关 `collapseOnSelectionFacet`、拖拽状态 `mouseSelectingField`、两种装饰策略代表 `livePreviewPlugin` 与 `mathWidget`，以及 KaTeX/图片双层缓存。

核心结论：整条数据流严格单向（用户动作→Transaction 三通道→不可变 EditorState→StateField/ViewPlugin 重算装饰→DOM），零件嵌在由 Facet（配置开关）、StateField（跨事务状态+块级装饰）、ViewPlugin（行内装饰+视口逻辑）、WidgetType（replace 出自定义 DOM）四种角色划分的固定工位上；`shouldShowSource` 不属任何一类，而是被共享的纯决策函数，把「Facet 开关 + 拖拽状态 + 选区相交」压成一个布尔值，作为「显示哪一面」的单一事实来源。

关键术语供后续承接：reading/live/source 三视图模式靠 `Compartment.reconfigure` 扩展组合切换而非内置字段，切 source 必须移除 `livePreviewPlugin`（只关 Facet 会得 reading 效果）；mark+CSS（同字符显隐、文本留 DOM、动画用 `max-width`/`font-size`）与 replace+Widget（视觉全不同、原文隐藏、块级强制走 StateField）的取舍；三类性能手段（拖拽跳过重建、双层缓存、选择性重建，失败结果不缓存以允许重试）；以及「设计文档是蓝图、`src/index.ts` 是模块化实现子集」这一贯穿全篇的差异视角。
