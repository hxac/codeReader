本讲讲解 verilog-ethernet 的 RTL 验证与仿真运行方式。核心工具链为 cocotb（用 Python 协程编写 testbench，经 VPI 与仿真时钟绑定，`await RisingEdge(clk)` 等待的是仿真时间而非墙钟时间）+ cocotbext-axi/cocotbext-eth（现成的 AXI-Stream、GMII 总线驱动）+ scapy（构造/解析报文）+ Icarus Verilog 仿真器。

`tb/` 下每个被测模块对应一个子目录，当前真正在用的是其中的 `Makefile` 与 `test_<模块>.py` 两件：`Makefile` 用 `VERILOG_SOURCES` 显式列出全部待编译 RTL（因 iverilog 不跨目录自动查找子模块），用统一的 `PARAM_` 前缀经 `-P` 注入模块参数，末尾 `include` cocotb 的 `Makefile.sim` 起仿真；`test_<模块>.py` 是「双用途」文件，既能被 `make` 加载，又作为 pytest 入口。需特别辨析：顶层 `tb/test_*.v` 与 `tb/test_*.py` 是 myhdl 时代的历史遗留（特征为 `$from_myhdl/$to_myhdl`、`from myhdl import`），当前流程不再编译，`tox.ini` 用 `--ignore-glob` 将其排除。

回归测试走 tox → pytest（`-n auto` 并行）→ cocotb-test → cocotb/iverilog 的调用链；`tox.ini` 锁定全部依赖的精确版本以保证可复现。运行方式：单模块用 `make` 或 `pytest tb/<模块>`，全套回归用 `tox`。本讲引入的关键术语：DUT、testbench、cocotb、cocotbext-axi/eth、cocotb-test、tox/pytest、`PARAM_` 参数约定、双用途测试文件。
