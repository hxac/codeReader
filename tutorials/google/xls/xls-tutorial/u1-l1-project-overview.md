## 2. 前置知识

在读源码之前，先用最通俗的方式铺垫三个概念。如果你已经熟悉，可以跳过本节。

### 2.1 什么是「硬件描述语言（HDL）」

传统上设计数字电路（芯片、FPGA）要写 **硬件描述语言（Hardware Description Language, HDL）**，最常见的是 Verilog 和 VHDL。HDL 描述的是「导线和逻辑门怎么连」「时钟每个上升沿寄存器怎么变」。它非常贴近物理实现，但也非常繁琐——实现一个简单的「两个数求最大公约数」都要操心时钟、寄存器、握手信号。

### 2.2 什么是「高层综合（HLS）」

**高层综合（High-Level Synthesis, HLS）** 的思路是：别让人类直接写门级/寄存器级细节，而是用一个**更接近软件**的语言描述「我要算什么」，然后由**工具自动**把它翻译成可综合的 Verilog。这里的「高层」是相对于 HDL 而言的——更接近算法、更远离晶体管。

一句话记忆：

> **HLS = 用「像写软件」的方式描述硬件功能，由工具自动生成 Verilog。**

### 2.3 什么是「软硬协同设计（Hardware/Software Co-design）」

现代系统里，CPU 跑通用软件、专用加速器（ASIC/FPGA）跑特定任务，两者要配合。「软硬协同设计」指的是软件工程师和硬件工程师**共享同一份设计描述、互相理解对方的成本模型**，而不是各干各的。XLS 正是为这种协作场景设计的——稍后你会看到它怎么做到「一份代码，软件硬件都能用」。

### 4.1 HLS 概念背景

#### 4.1.1 概念说明

硬件设计的痛点在于：直接写 HDL 太底层、迭代太慢。而纯粹的软件又跑不出硬件的**性能**和**能效**。HLS 想填的就是中间这道鸿沟——让人用高层语言快速表达算法意图，再由工具自动做「调度（哪个运算放在哪个时钟周期）」「分配资源」「插流水线寄存器」等繁琐的底层决策。

XLS 把这件事放在了一个更大的时代背景下：**摩尔定律终结（End of Moore's Law, EoML）**。通用 CPU 不再能靠工艺升级白拿性能，于是业界进入「专用化（age of specialization）」——越来越多功能要用专用硬件加速器来实现。这意味着硬件设计的数量和频率都在上升，传统手写 HDL 的方式跟不上需求，必须靠自动化工具来加速。

#### 4.1.2 核心流程

从「高层描述」到「可综合 Verilog」，一条典型的 HLS 流水线是这样的（这也是整本手册后续要逐层拆解的主干）：

```text
高层语言描述（算法意图）
        │
        ▼  前端：DSLX 或 C++(xlscc)
   XLS 中间表示（IR）   ← 编译器的「枢纽」，后续所有阶段都在它之上
        │
        ▼  优化 Pass（化简、消重、折叠常量……）
   优化后的 IR
        │
        ▼  流水线调度（把运算分配到时钟周期 / 流水线级）
   带时序的 IR（Block）
        │
        ▼  代码生成（codegen）
   可综合的 Verilog / SystemVerilog
```

你现在不需要理解每一步的细节，只要记住：**XLS 的全部工作就是把左边的高层描述，沿这条流水线变成右边的 Verilog**。后面的每一篇讲义，其实都是在拆这条流水线上的某一段。

紧接着，README 把项目放到了 EoML 时代背景下：

#### 4.1.5 小练习与答案

**练习 1**：用自己的话解释「为什么 EoML（摩尔定律终结）会让 HLS 变得更重要」？

> **参考答案**：摩尔定律终结后，通用 CPU 难以靠工艺升级继续提升性能，业界转向用专用硬件加速器来获取性能与能效。专用硬件数量和迭代频率都在上升，而传统手写 HDL 又慢又底层，因此需要 HLS 工具来自动化地把高层算法描述翻译成硬件，跟上专用化的节奏。XLS 自我定位正是「EoML 时代的 SDK」。

**练习 2**：在 HLS 流水线里，「IR（中间表示）」处于什么位置、起什么作用？

> **参考答案**：IR 处于「前端（高层语言）」和「后端（代码生成）」之间，是整条流水线的枢纽。前端把高层描述翻译成 IR，后续的优化、调度、代码生成都直接在 IR 上进行。这样做的好处是：前端只关心「怎么把语言翻译成 IR」，后端只关心「怎么把 IR 翻译成 Verilog」，两边解耦，各自演进。

### 4.2 README 项目定位

#### 4.2.1 概念说明

在动手之前，我们要搞清楚 XLS **当前是什么状态**、**用什么协议**、**支持哪些建模能力**。这些信息直接决定了你该用什么心态去用它（比如：它是实验性的，别指望像成熟商业工具那样稳定）。

#### 4.2.2 核心流程

了解一个开源项目的「定位」，通常按这个清单过一遍：

```text
1. 它解决什么问题？       → High Level Synthesis（已在 4.1 讲过）
2. 它的成熟度如何？       → 实验性、快速迭代、非官方支持产品
```

### 4.3 同一设计、两种身份：XLS 的核心理念

这是本讲最重要的一节。理解了它，你就抓住了 XLS 区别于传统 HDL 流程的灵魂。

#### 4.3.1 概念说明

传统硬件流程有一个长期痛点：**算法先用 C/C++/Python 验证，再由硬件工程师人工「翻译」成 Verilog，两边各维护一份，极易不一致**。验证它们功能相同（软件模型 vs 硬件实现）往往要耗费巨大精力。

XLS 的核心理念是颠覆这一点：**同一份设计，既能以接近原生的速度当主机软件跑，也能生成硬件模块——而且工具保证（甚至提供形式化验证手段证明）两者功能完全相同。** 这样软件工程师和硬件工程师共享同一份「真值来源（single source of truth）」，不再需要人工同步两套代码。

支撑这个理念的有两条**前端入口**——也就是「用什么语言写这份共享设计」：

1. **DSLX**：XLS 团队主推的领域专用语言（DSL），模仿 Rust，是一种不可变、表达式式、面向硬件的数据流语言。
2. **C++（xlscc）**：由 Google 另一个团队开发的实验性 C++ 语法前端，把 C++ 翻译成 XLS IR，适合已有 C++ HLS 代码积累的团队。

两条入口殊途同归——都把高层代码翻译成同一份 XLS IR，之后再走完全相同的优化→调度→代码生成流程。

#### 4.3.2 核心流程

「同一设计、两种身份」在 XLS 里是这样落地的：

```text
              ┌── DSLX（主推的 Rust 风格 DSL）──┐
高层代码 ─────┤                                 ├──► XLS IR ──► 优化 ──► 调度 ──► Verilog
              └── C++ (xlscc，实验性) ─────────┘
                        │
                        │  （同一份 IR 还可以被）
                        ├──► IR 解释器 / JIT ──► 当主机软件、原生速度运行
                        └──► 仿真器 / 形式化求解器 ──► 验证生成的硬件与软件模型等价
```

关键在于：**中间的 XLS IR 是唯一的「真相之锚」**。无论你用 DSLX 还是 C++ 进来，无论你拿它去跑软件还是生成硬件，都是同一份 IR 在驱动。这就是「软件/硬件协同」在工程上得以实现的基础。

#### 4.3.3 源码精读

先看核心理念的原文表述：

[README.md:L26-L30](https://github.com/google/xls/blob/e796ea8aeea3875362c7dbeb11a850f3854a9116/README.md#L26-L30) —— 这段是整个理念的浓缩：XLS 能快速开发**硬件 IP**，而这份 IP 同时又能作为高效的**主机软件**运行；XLS 工具不仅保证两者功能相同，还**提供工具帮助形式化验证（formally verify）**它们功能一致。请把「runs as host software」和「generates hardware」这两个短语画上重点。

再看两条前端入口在 README 里的官方描述。第一条是主推的 DSLX：

[README.md:L256-L262](https://github.com/google/xls/blob/e796ea8aeea3875362c7dbeb11a850f3854a9116/README.md#L256-L262) —— 这段把 DSLX 定义为「模仿 Rust、不可变的表达式式数据流 DSL」，强调它带有硬件导向特性：**任意位宽（arbitrary bitwidths）、全定长对象、完全可分析的调用图**。注意它解释了「为什么选数据流 DSL」：相比那些假设冯·诺依曼计算模型的语言，数据流 DSL 更适合描述硬件。

第二条是 C++ 前端 xlscc：

[README.md:L243-L247](https://github.com/google/xls/blob/e796ea8aeea3875362c7dbeb11a850f3854a9116/README.md#L243-L247) —— 这段说 `contrib/xlscc` 提供**实验性的 C++ 语法支持**，目标是 XLS IR，是 **DSLX 之外的另一条路径**，由 Google 的一个兄弟团队开发，与 XLS 其余部分共用同一套开源/测试流程。对「已有 C++ HLS 代码库」的团队特别有价值。

为了让你直观感受「硬件语言也能像软件一样调试」，再看官方第一篇教程里那个最小的 DSLX 例子：

[docs_src/tutorials/hello_xls.md:L45-L50](https://github.com/google/xls/blob/e796ea8aeea3875362c7dbeb11a850f3854a9116/docs_src/tutorials/hello_xls.md#L45-L50) —— 这是一个完整的 DSLX 函数 `hello_xls`，接收一个 11 字符的 `u8` 数组，用内置的 `trace!` 把它打印出来。注意它读起来就像普通软件函数——这正是 XLS 想要的体验。

而它运行后的输出，能让你理解「硬件里信号其实就是数字」：

[docs_src/tutorials/hello_xls.md:L117-L130](https://github.com/google/xls/blob/e796ea8aeea3875362c7dbeb11a850f3854a9116/docs_src/tutorials/hello_xls.md#L117-L130) —— 输出里 `"Hello, XLS!"` 被打印成一串数字 `[72, 101, 108, ...]`。教程解释：这些数字正是各字符的 ASCII 码。设计/调试硬件时，信号更常以数字而非字符串出现，所以这里就用数字表示。这个小例子恰好印证了 XLS「软件式开发体验」+「硬件本质是数值信号」的双重身份。

#### 4.3.5 小练习与答案

**练习 1**：用一句话说出 XLS 区别于传统 HDL 设计流程的最核心特点。

> **参考答案**：XLS 让**同一份设计**既能以接近原生的速度当主机软件运行，又能生成可综合硬件模块，并提供（含形式化验证在内的）工具保证两者功能一致——从而让软件和硬件共享同一份「真相来源」，免去人工同步两套代码。

**练习 2**：DSLX 和 C++(xlscc) 这两条前端入口，最终汇入的「共同终点」是什么？为什么这个设计很重要？

> **参考答案**：它们都汇入 **XLS IR（中间表示）**。这很重要，因为 IR 是唯一的真相之锚：前端可以有多个（DSLX、C++），后端也可以有多个（解释器、JIT、codegen、仿真、形式化验证），但只要都以同一份 IR 为中心，就能保证「软件身份」和「硬件身份」功能一致，也方便工具链各阶段独立演进、解耦维护。

**练习 3**：DSLX 被描述为「数据流 DSL」。根据 README，XLS 团队为什么认为数据流 DSL 比传统语言更适合描述硬件？

> **参考答案**：README 指出，传统语言大多**假设冯·诺依曼计算模型**（顺序、内存等），而硬件本质上是无序的数据流。数据流 DSL（不可变、表达式式、定长）更贴近硬件的本质，因此更适合描述硬件。

## 6. 本讲小结

- XLS 是一个 **High Level Synthesis（高层综合）工具链**，把灵活的高层功能描述翻译成可综合的 Verilog / SystemVerilog，Apache 2 开源。
- 它把自身放在 **EoML（摩尔定律终结）时代** 的背景下，定位为「专用化时代」的软硬协同 SDK。
- XLS 最核心理念是：**同一份设计既能当主机软件原生运行，又能生成硬件**，并提供（含形式化验证在内的）手段保证两者功能一致。
- 它能建模两类抽象：偏组合的 **Function（函数）** 和偏时序状态的 **Proc（进程）**。
- 它有两条前端入口：主推的 **DSLX**（`xls/dslx`）和实验性的 **C++/xlscc**（`xls/contrib/xlscc`），两者都汇入同一份 **XLS IR**。
- 项目目前是**实验性、快速迭代**状态，使用时要有「踩坑+贡献」的心态。
